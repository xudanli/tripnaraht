## 项目概述

### 项目特点分析

基于后端API分析，本项目具有以下特点：

1. **业务复杂度**: 中等偏高
   - 涉及行程管理、地点推荐、路线优化等复杂业务逻辑
   - 需要处理大量数据展示和交互

2. **数据特点**:
   - 大量列表数据（行程列表、地点列表等）
   - 复杂嵌套数据结构（行程-行程项-地点）
   - 实时数据需求（价格、路线追踪）

3. **交互特点**:
   - 地图展示和交互（地点、路线）
   - 时间轴/日历视图（行程安排）
   - 表单操作频繁（创建、编辑行程）

4. **技术要求**:
   - TypeScript支持（后端使用TypeScript）
   - 多终端支持（PC为主，移动端为辅）
   - 国际化支持（多国家/多语言）

5. **终端形式特点**:
   - **PC端主导**: 复杂的行程规划、决策分析、数据可视化
   - **移动端辅助**: 实时追踪、行程查看、导航功能

### 技术选型原则

- **类型安全**: 优先选择TypeScript友好的方案
- **开发效率**: 选择成熟生态、开发体验好的技术
- **性能优化**: 考虑首屏加载、运行时性能
- **可维护性**: 代码结构清晰、易于扩展
- **团队协作**: 选择学习成本低、文档完善的技术

## 终端形式选择

### 推荐方案：PC端为主 + 移动端为辅

基于项目功能特点分析，建议采用**PC端为主，移动端为辅**的混合方案。

#### PC端场景（主要使用场景）

**适用功能**:
1. **复杂行程规划** ⭐⭐⭐⭐⭐
   - 创建和编辑行程（需要填写复杂表单）
   - 行程项管理（拖拽排序、时间调整）
   - 预算配置和节奏策略设置
   - 地图上选择地点和规划路线（需要大屏幕）

2. **决策分析工具** ⭐⭐⭐⭐⭐
   - What-If评估（蒙特卡洛模拟，需要展示复杂数据）
   - 稳健度分析（风险等级、缓冲时间等统计）
   - 路线优化（需要查看地图和时间轴）

3. **数据可视化** ⭐⭐⭐⭐⭐
   - 时间轴视图（展示多天行程，PC屏幕更合适）
   - 地图交互（查看路线、选择地点）
   - 统计图表（费用分布、行程密度等）
   - 复盘报告（PDF导出、数据表格）

4. **复杂表单操作** ⭐⭐⭐⭐
   - 创建行程（目的地、日期、预算、旅行者信息）
   - 编辑行程项（时间、地点、备注）
   - 配置决策策略（Abu/Dr.Dre/Neptune策略选择）

**PC端优势**:
- ✅ 大屏幕适合展示复杂信息
- ✅ 鼠标操作精确（地图交互、拖拽）
- ✅ 多窗口操作（对比不同方案）
- ✅ 键盘输入效率高

#### 移动端场景（辅助使用场景）

**适用功能**:
1. **实时追踪** ⭐⭐⭐⭐⭐
   - 徒步路线实时追踪（`POST /trails/tracking/start`）
   - GPS位置上报（每10秒或每50米）
   - 轨迹偏差显示
   - 统计信息实时更新

2. **行程进行中** ⭐⭐⭐⭐
   - 查看当前行程状态（`GET /trips/:id/state`）
   - 下一站查询（语音助手："下一站是哪里？"）
   - 行程导航（显示当前活动、下一站信息）
   - 行程项打卡（标记已完成的活动）

3. **快速查看** ⭐⭐⭐
   - 查看行程列表
   - 查看行程详情（简化版时间轴）
   - 查看地点信息
   - 查看天气和准备度提醒

4. **语音交互** ⭐⭐⭐
   - 语音创建行程（`POST /trips/from-natural-language`）
   - 语音查询（"下一站是哪里？"）
   - 语音导航指令

**移动端优势**:
- ✅ GPS定位精确
- ✅ 便携性强（户外使用）
- ✅ 实时通知推送
- ✅ 语音交互自然

#### 混合方案设计建议

##### 方案一：响应式Web应用（推荐）⭐

**技术选型**: React + 响应式设计（PC + 移动端共用代码）

**优点**:
- ✅ 一套代码，维护成本低
- ✅ 开发效率高
- ✅ 数据同步简单（共用API）

**缺点**:
- ⚠️ PC和移动端体验可能不够极致
- ⚠️ 移动端性能可能不如原生应用

**实现建议**:
- 使用响应式布局（Tailwind CSS / CSS Grid）
- PC端显示完整功能（侧边栏、多列布局）
- 移动端简化界面（底部导航、单列布局）
- 地图组件适配不同屏幕尺寸
- 移动端优化触摸交互

##### 方案二：PC Web + 移动端原生App

**技术选型**: 
- PC: React Web应用
- 移动端: React Native（如果团队熟悉React）

**优点**:
- ✅ 各端体验最优化
- ✅ 移动端性能更好
- ✅ 可以调用原生功能（GPS、相机、推送）

**缺点**:
- ❌ 维护两套代码，成本高
- ❌ 需要React Native团队
- ❌ 数据同步需要额外处理

**适用场景**: 
- 预算充足
- 团队有移动端开发能力
- 对移动端体验要求极高

##### 方案三：PC Web + 移动端PWA

**技术选型**: React + PWA（渐进式Web应用）

**优点**:
- ✅ 接近原生体验（离线、推送、安装）
- ✅ 一套代码维护
- ✅ 无需应用商店审核

**缺点**:
- ⚠️ iOS对PWA支持有限
- ⚠️ 某些原生功能无法调用

**实现建议**:
- 使用Service Worker实现离线缓存
- 使用Web Push API实现推送通知
- 使用Web App Manifest实现安装提示
- 移动端优化为单页应用（SPA）

#### 推荐实施策略

**阶段一：PC端优先** ⭐⭐⭐⭐⭐
1. 先开发PC端完整功能
2. 确保核心功能（行程规划、决策分析）完善
3. 验证业务流程和用户体验

**阶段二：移动端简化版** ⭐⭐⭐⭐
1. 实现响应式设计，支持移动端浏览
2. 重点优化移动端关键功能：
   - 实时追踪（必须原生体验）
   - 行程查看
   - 下一站查询

**阶段三：移动端增强** ⭐⭐⭐
1. 如需要，开发React Native应用
2. 或优化PWA体验
3. 实现移动端专属功能（推送、离线等）

#### 移动端功能优先级

| 功能 | 优先级 | PC端 | 移动端 | 说明 |
|------|--------|------|--------|------|
| 行程规划 | P0 | ✅ | ❌ | 复杂操作，PC端更合适 |
| 决策分析 | P0 | ✅ | ❌ | 需要大屏幕展示数据 |
| 实时追踪 | P0 | ❌ | ✅ | 移动端专属功能 |
| 行程查看 | P1 | ✅ | ✅ | 两端都需要 |
| 下一站查询 | P1 | ✅ | ✅ | 移动端更重要 |
| 地点搜索 | P1 | ✅ | ✅ | 两端都需要 |
| 路线导航 | P2 | ✅ | ✅ | 移动端更重要 |

## 技术栈选型

### 框架选择

#### 推荐方案：React 18 + TypeScript

**选择理由**:

1. **生态成熟**: React拥有最丰富的生态系统和社区支持
2. **类型支持**: TypeScript支持完善，类型推断能力强
3. **组件化**: 符合项目模块化需求
4. **性能优化**: React 18的并发特性、Suspense、代码分割等

**版本选择**:
- React: `^18.2.0`
- TypeScript: `^5.0.0`

#### 备选方案：Vue 3 + TypeScript

**适用场景**: 如果团队更熟悉Vue生态

**优势**:
- 学习曲线相对平缓
- 组合式API设计优雅
- 性能优秀

**劣势**:
- 生态相对React略小
- 大型项目经验相对较少

### React vs Vue 详细对比

#### 为什么推荐React？基于项目特点的分析

基于本项目的特点（行程规划系统、复杂业务逻辑、地图交互、实时数据），以下是选择React的具体理由：

##### 1. **生态系统成熟度** ⭐⭐⭐⭐⭐

**React优势**:
- **地图集成**: 
  - React生态中有更多成熟的地图库（react-leaflet、react-map-gl、@react-google-maps/api）
  - Mapbox官方提供React组件库（@mapbox/mapbox-gl-react）
  - 本项目的核心功能是路线规划，地图展示是关键需求
  
- **UI组件库选择更丰富**:
  - Ant Design（企业级后台首选，本项目适合）
  - Material-UI（MUI）
  - shadcn/ui + Tailwind（现代化定制方案）
  
- **状态管理生态**:
  - React Query（TanStack Query）与React深度集成
  - Redux Toolkit官方维护，文档完善
  - Zustand、Jotai等轻量方案丰富

**Vue生态对比**:
- Vue的地图库相对较少，主要是vue2-google-maps、vue-leaflet
- UI组件库：Element Plus、Ant Design Vue、Vuetify（选择相对较少）
- 状态管理：Pinia（官方推荐，但生态相对Redux较小）

##### 2. **复杂业务逻辑处理** ⭐⭐⭐⭐⭐

**本项目特点**: 涉及行程决策引擎、多策略系统、路线优化等复杂逻辑

**React优势**:
- **Hooks模式更适合复杂逻辑抽象**:
  ```typescript
  // React: 可以方便地抽象复杂业务逻辑
  function useTripOptimization(tripId: string) {
    const [optimization, setOptimization] = useState();
    const [loading, setLoading] = useState(false);
    // 复杂的优化逻辑封装
    return { optimization, optimize, loading };
  }
  ```
  
- **函数式编程范式**:
  - 更符合复杂算法的实现方式
  - 易于单元测试
  - 代码可预测性强

**Vue对比**:
- Composition API虽然强大，但在复杂逻辑抽象方面，Hooks模式更成熟
- 响应式系统虽然方便，但对于复杂计算可能产生不必要的响应

##### 3. **TypeScript支持** ⭐⭐⭐⭐

**React + TypeScript**:
- **类型推断更强**: React 18 + TypeScript 5的组合非常成熟
- **泛型支持好**: 组件泛型、Hooks泛型使用方便
- **类型工具完善**: 大量类型定义文件（@types/*）

**Vue + TypeScript**:
- Vue 3的TypeScript支持已经很好了
- 但在复杂组件类型推断上，React稍胜一筹
- 模板语法在TypeScript中需要额外的类型声明

##### 4. **性能优化能力** ⭐⭐⭐⭐

**React优势**:
- **React 18并发特性**: 
  - Concurrent Rendering（并发渲染）
  - Suspense（数据加载状态管理）
  - startTransition（非紧急更新）
  - 对于本项目的实时数据更新、地图交互优化很有帮助
  
- **代码分割成熟**: 
  - React.lazy + Suspense
  - 路由级别的代码分割（React Router）
  - 组件级别的动态导入

**Vue对比**:
- Vue 3性能已经很优秀（虚拟DOM优化、编译时优化）
- 但React 18的并发特性是Vue目前没有的
- 对于需要处理大量实时更新的场景（如路线追踪），React的并发特性更有优势

##### 5. **团队和招聘** ⭐⭐⭐⭐⭐

**React优势**:
- **人才市场更大**: React开发者数量远超Vue
- **学习资源丰富**: 教程、文档、社区资源更多
- **大型项目经验**: 更多React大型项目案例可参考
- **企业采用率高**: 更多企业选择React，迁移成本低

**Vue对比**:
- 国内Vue开发者也不少，但整体市场占有率低于React
- 大型项目案例相对较少（但也不少）

##### 6. **第三方库集成** ⭐⭐⭐⭐

**本项目需要的第三方库**:
- Mapbox / Leaflet（地图）
- Chart.js / Recharts（图表，行程统计）
- Date picker（日期选择，行程日期）
- 拖拽库（行程项排序）

**React生态**:
- 所有这些需求都有成熟的React集成库
- 官方或社区维护，更新及时

**Vue生态**:
- 同样有对应库，但选择相对较少
- 某些库可能需要自己封装

#### Vue 3的优势场景（如果选择Vue）

Vue 3在某些方面确实有优势，但不太符合本项目需求：

1. **学习曲线平缓**: 如果团队都是新手，Vue更容易上手
2. **模板语法直观**: 对于简单页面，模板语法更直观
3. **单文件组件**: .vue文件将模板、脚本、样式集中，组织方式清晰
4. **官方工具链**: Vue CLI、Vite（Vue团队开发）等官方工具完善

但本项目是**复杂业务系统**，不是简单页面，Vue的这些优势不是决定性因素。

#### 综合建议

**选择React的理由总结**:

1. ✅ **项目需求匹配**: 复杂业务逻辑、地图交互、实时数据更新
2. ✅ **生态成熟**: 地图、图表、UI库选择丰富
3. ✅ **性能优化**: React 18并发特性适合实时交互场景
4. ✅ **团队协作**: 人才资源丰富，学习资料多
5. ✅ **长期维护**: React生态更活跃，长期维护更有保障

**选择Vue的理由**（如果团队强烈倾向Vue）:

1. ✅ 团队更熟悉Vue
2. ✅ 学习曲线更平缓
3. ✅ 官方工具链完善
4. ⚠️ 但需要自己封装更多组件和库
5. ⚠️ 地图集成相对复杂

#### 实际建议

**如果团队对Vue非常熟悉**，选择Vue 3 + TypeScript也是完全可行的。两个框架都能完成项目需求，React的优势更多在于生态和工具链，而不是核心功能实现能力。

**最终决策因素**:
- 团队技术栈熟悉度（最重要）
- 项目长期维护考虑
- 招聘和团队扩展考虑
- 第三方库需求

#### 补充说明：Next.js vs Vite + React Router

**本项目已有Next.js配置**，这里需要说明两个方案的区别：

##### 方案A：Next.js 14 (App Router)

**适合场景**:
- ✅ 需要SSR/SSG（服务端渲染/静态生成）
- ✅ 需要SEO优化（行程分享页面、地点详情页面）
- ✅ 需要文件系统路由（自动路由生成）
- ✅ 需要API Routes（在Next.js中写API）

**优势**:
- 开箱即用的SSR/SSG
- 优秀的SEO支持
- 内置图片优化、字体优化
- Vercel部署优化（Next.js团队开发）

**劣势**:
- 学习成本较高（App Router是新的，文档相对较少）
- 配置相对复杂
- 对于纯前端应用，可能过于重量级

##### 方案B：Vite + React Router（推荐用于本项目）

**适合场景**:
- ✅ 纯前端应用（SPA）
- ✅ 不需要SSR/SSG
- ✅ 更灵活的配置
- ✅ 更快的开发体验

**优势**:
- 开发体验极佳（HMR速度极快）
- 配置简单直观
- 构建产物更小
- 更适合纯前端应用

**劣势**:
- 没有SSR/SSG
- SEO不友好（但可以用其他方案解决，如预渲染）

##### 本项目建议

**建议使用 Vite + React Router**，原因：

1. **项目是内部管理系统或工具应用**，不太需要SEO
2. **开发体验更好**，Vite的HMR速度远超Next.js
3. **配置更简单**，更容易上手
4. **如果需要分享功能**，可以：
   - 使用预渲染服务（Prerender.io）
   - 或者单独为分享页面使用Next.js
   - 或者后端直接生成HTML

**如果已经确定使用Next.js**，也是完全可行的选择，只需要注意：
- 使用App Router（Next.js 13+推荐）
- 理解Server Components和Client Components的区别
- 配置API代理（如果需要调用后端API）

## 状态管理方案

### 推荐方案：Redux Toolkit (RTK) + React Query

#### 为什么选择Redux Toolkit + React Query？

**数据特点分析**:
- **服务器状态**: 行程、地点、酒店等数据主要来自API
- **客户端状态**: UI状态、表单状态、用户偏好设置
- **缓存需求**: 列表数据、详情数据需要缓存
- **实时更新**: 部分数据需要实时刷新

#### 方案组合说明

**React Query (TanStack Query)** - 管理服务器状态
- ✅ 自动缓存管理
- ✅ 请求去重
- ✅ 后台数据同步
- ✅ 乐观更新支持
- ✅ 分页、无限滚动支持

**Redux Toolkit** - 管理客户端状态
- ✅ UI状态（侧边栏、模态框等）
- ✅ 表单状态（复杂表单）
- ✅ 全局配置
- ✅ 用户偏好设置

### React Query 使用示例

```typescript
// hooks/useTrips.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { tripsApi } from '@/api/trips';

export function useTrips() {
  return useQuery({
    queryKey: ['trips'],
    queryFn: () => tripsApi.getAll(),
    staleTime: 5 * 60 * 1000, // 5分钟
  });
}

export function useTrip(id: string) {
  return useQuery({
    queryKey: ['trips', id],
    queryFn: () => tripsApi.getById(id),
    enabled: !!id,
  });
}

export function useCreateTrip() {
  const queryClient = useQueryClient();
  
  return useMutation({
    mutationFn: tripsApi.create,
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['trips'] });
    },
  });
}
```

### Redux Toolkit 使用示例

```typescript
// store/slices/uiSlice.ts
import { createSlice, PayloadAction } from '@reduxjs/toolkit';

interface UIState {
  sidebarOpen: boolean;
  theme: 'light' | 'dark';
}

const initialState: UIState = {
  sidebarOpen: false,
  theme: 'light',
};

const uiSlice = createSlice({
  name: 'ui',
  initialState,
  reducers: {
    toggleSidebar: (state) => {
      state.sidebarOpen = !state.sidebarOpen;
    },
    setTheme: (state, action: PayloadAction<'light' | 'dark'>) => {
      state.theme = action.payload;
    },
  },
});

export const { toggleSidebar, setTheme } = uiSlice.actions;
export default uiSlice.reducer;
```

### 状态管理最佳实践

1. **服务器状态优先使用React Query**
   - API数据获取
   - 列表数据
   - 详情数据

   - 全局UI状态
   - 复杂表单状态（跨组件共享）
   - 用户设置和偏好

3. **本地状态使用useState**
   - 组件内部状态
   - 简单的UI状态（按钮loading等）

**优势**:

**劣势**:

## API请求方案

### 推荐方案：Axios + React Query

#### Axios配置

```typescript
// api/client.ts
import axios from 'axios';

const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || 'http://localhost:3000',
  timeout: 10000,
  headers: {
    'Content-Type': 'application/json',
  },
});

// 请求拦截器
apiClient.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('token');
    if (token) {
      config.headers.Authorization = `Bearer ${token}`;
    }
    return config;
  },
  (error) => Promise.reject(error)
);

// 响应拦截器
apiClient.interceptors.response.use(
  (response) => response.data,
  (error) => {
    if (error.response?.status === 401) {
      // 处理未授权
      localStorage.removeItem('token');
      window.location.href = '/login';
    }
    return Promise.reject(error);
  }
);

export default apiClient;
```

#### API模块化封装

```typescript
// api/trips.ts
import apiClient from './client';
import type { Trip, CreateTripDto, UpdateTripDto } from './types';

export const tripsApi = {
  // 获取所有行程
  getAll: (): Promise<Trip[]> => {
    return apiClient.get('/trips');
  },
  
  // 获取行程详情
  getById: (id: string): Promise<Trip> => {
    return apiClient.get(`/trips/${id}`);
  },
  
  // 创建行程
  create: (data: CreateTripDto): Promise<Trip> => {
    return apiClient.post('/trips', data);
  },
  
  // 更新行程
  update: (id: string, data: UpdateTripDto): Promise<Trip> => {
    return apiClient.put(`/trips/${id}`, data);
  },
  
  // 删除行程
  delete: (id: string): Promise<void> => {
    return apiClient.delete(`/trips/${id}`);
  },
};
```

## 常见问题解答

### Q0: 为什么选择React而不是Vue？

**A**: 这是一个很好的问题。虽然Vue 3也是很优秀的框架，但基于本项目特点，选择React更合适：

1. **生态匹配度**: 
   - 本项目核心需求是地图交互和路线规划
   - React生态中有更多成熟的地图库（react-leaflet、@react-google-maps/api等）
   - Mapbox官方提供React组件库支持

2. **复杂业务逻辑**:
   - 本项目涉及决策引擎、路线优化等复杂算法
   - React Hooks模式更适合复杂逻辑抽象
   - 函数式编程范式更符合算法实现

3. **性能需求**:
   - 实时路线追踪、地图交互需要频繁更新
   - React 18的并发特性更适合这种场景

4. **团队和长期维护**:
   - React开发者更多，招聘更容易
   - 生态更活跃，长期维护更有保障

**但是**，如果团队对Vue非常熟悉，Vue 3 + TypeScript也是完全可行的选择。两个框架都能完成项目需求，React的优势更多在于生态和工具链。

详细对比请参考[React vs Vue详细对比](#react-vs-vue-详细对比)章节。

### Q1: 为什么选择React Query + Redux Toolkit的组合？

**A**: 这是一个常见的误解。实际上，对于大多数场景，只需要React Query即可：
- **服务器状态**（API数据）→ React Query管理
- **客户端状态**（UI状态）→ React本地状态（useState/useReducer）
- **全局UI状态**（如侧边栏开关）→ React Context或Zustand

Redux Toolkit主要用于**复杂状态管理场景**，如果项目状态管理需求较简单，可以只用React Query + Context API。

### Q2: 移动端适配方案如何选择？

**A**: 基于本项目特点，推荐**响应式Web应用**作为主要方案：

1. **响应式设计**（推荐）: 
   - 使用CSS媒体查询，一套代码适配多端
   - PC端显示完整功能，移动端简化界面
   - 开发维护成本低

2. **PWA**（后续考虑）:
   - 渐进式Web应用，接近原生体验
   - 支持离线、推送、安装
   - 适合移动端增强功能

3. **React Native**（可选）:
   - 如果需要极致移动端体验
   - 特别是实时追踪功能（GPS、离线地图）
   - 需要额外团队和预算

**本项目建议**: 
- 先做响应式Web，确保PC端体验完善
- 移动端重点优化实时追踪、行程查看等核心功能
- 如果用户反馈需要更好的移动端体验，再考虑React Native

### Q3: 如何处理大列表性能问题？

**A**: 几种方案组合使用：
- **虚拟滚动**: react-window或react-virtualized
- **分页加载**: 后端分页 + 前端分页器
- **无限滚动**: React Query的useInfiniteQuery
- **图片懒加载**: loading="lazy"属性

### Q4: 如何确保类型安全？

**A**: 
1. 使用TypeScript严格模式
2. 从后端Swagger自动生成类型定义（OpenAPI Generator）
3. 避免使用`any`类型
4. 为API响应定义明确的类型
5. 使用类型守卫函数

### Q5: 如何进行错误监控？

**A**: 推荐接入错误监控服务：
- **Sentry**: 功能全面，提供错误追踪和性能监控
- **LogRocket**: 可以录制用户会话，便于调试
- **自建方案**: 错误上报到自己的后端

```typescript
// 错误边界示例
class ErrorBoundary extends React.Component {
  componentDidCatch(error, errorInfo) {
    // 上报错误到监控服务
    Sentry.captureException(error, { extra: errorInfo });
  }
}
```

## 最佳实践总结

### 1. 代码组织

✅ **DO**:
- 按功能模块组织代码
- 组件尽量小且单一职责
- 抽离可复用的业务逻辑到Hooks
- 使用TypeScript严格模式

❌ **DON'T**:
- 不要创建过大的组件文件（>300行考虑拆分）
- 不要将业务逻辑写在组件中
- 不要在组件中直接使用fetch，应该封装到API层

### 2. 性能优化

✅ **DO**:
- 使用React.memo优化组件渲染
- 使用useMemo和useCallback合理缓存
- 实现代码分割和懒加载
- 优化图片大小和格式

❌ **DON'T**:
- 不要过早优化
- 不要滥用useMemo和useCallback
- 不要忽略React DevTools的性能分析

### 3. 状态管理

✅ **DO**:
- 优先使用React Query管理服务器状态
- 本地状态优先使用useState
- 复杂状态考虑useReducer
- 跨组件状态使用Context或状态管理库

❌ **DON'T**:
- 不要将所有状态都放在Redux中
- 不要在组件中直接操作DOM
- 不要忘记清理副作用（useEffect清理函数）

### 4. 类型定义

✅ **DO**:
- 从后端API自动生成类型
- 为所有Props定义类型
- 使用联合类型而不是any
- 使用类型守卫函数

❌ **DON'T**:
- 不要使用any类型
- 不要忽略TypeScript错误
- 不要使用@ts-ignore（除非必要）

### 5. 测试

✅ **DO**:
- 测试用户行为而不是实现细节
- 为关键业务逻辑编写测试
- 使用React Testing Library
- 编写可维护的测试代码

❌ **DON'T**:
- 不要追求100%覆盖率
- 不要测试框架本身
- 不要编写脆弱的测试

## 迁移指南（如有旧项目）

如果是从其他技术栈迁移，请参考：

### 从Vue迁移到React

1. 组件结构对应关系
   - Vue组件 → React函数组件
   - Vuex → Redux Toolkit / Zustand
   - Vue Router → React Router

2. 生命周期对应
   - `mounted` → `useEffect(() => {}, [])`
   - `beforeUnmount` → `useEffect(() => { return cleanup }, [])`

### 从Class组件迁移到函数组件

1. Class组件 → 函数组件 + Hooks
2. `this.state` → `useState`
3. `componentDidMount` → `useEffect`
4. `componentDidUpdate` → `useEffect` with dependencies
