**优化日期**: 2025-01-14  
**优化角色**: 架构师  
**目标**: 审查当前架构，提出更优的架构方案

## 🔍 当前架构分析

### 当前实现方式

**验证位置**：`ClaudeOrchestratorService.validatePlanInputs`

**验证时机**：
```
1. 分析用户意图 (LLM)
2. 选择路由策略 (LLM)
3. 选择 Skills (LLM)
4. 编排执行计划 (LLM)
5. ✅ 验证计划输入参数（当前实现）
6. 执行计划
```

**验证方式**：
```typescript
// 硬编码的验证规则
if (step.skillName === 'decision.runThreeGuardians') {
  if (!input.world && !input.tripId && !actualTripId) {
    missingParams.push('world 或 tripId');
  }
} else if (step.skillName === 'world.buildContext') {
  // ...
}
```

### 架构问题分析

#### 问题 1：硬编码验证规则

**问题**：
- 每个 skill 的验证逻辑都硬编码在 `validatePlanInputs` 中
- 新增 skill 需要手动添加验证规则
- 验证逻辑与 skill 内部验证可能重复
- 维护成本高，容易遗漏

**影响**：
- ❌ 可扩展性差
- ❌ 维护成本高
- ❌ 容易出错

#### 问题 2：验证时机过晚

**问题**：
- 验证在 plan 编排之后，已经消耗了 3 次 LLM 调用（意图分析、路由决策、Skills 选择、计划编排）
- 如果验证失败，前面的 LLM 调用成本浪费

**影响**：
- ❌ 成本浪费（LLM 调用成本）
- ❌ 响应时间仍然较长（~5-10 秒）

#### 问题 3：验证逻辑不完整

**问题**：
- 只验证了 3 个 skill（`decision.runThreeGuardians`、`world.buildContext`、`routeDirection.pickForIntent`）
- 其他 skill 的验证规则缺失
- 参数依赖关系无法处理（某些参数依赖前面步骤的结果）

**影响**：
- ❌ 验证覆盖不完整
- ❌ 某些 skill 仍然可能执行失败

#### 问题 4：参数提取逻辑复杂

**问题**：
- `prepareSkillInput` 包含复杂的参数提取逻辑
- 验证时使用的输入可能与实际执行时的输入有差异
- 参数提取逻辑分散在多个地方

**影响**：
- ❌ 验证准确性可能不足
- ❌ 代码复杂度高

## ✅ 优化方案

### 方案 1：基于 Skill Metadata 的声明式验证（推荐）

#### 核心思想

**将验证规则定义在 Skill Metadata 中，实现声明式验证**

#### 架构设计

**1. 扩展 SkillMetadata 接口**

```typescript
export interface SkillMetadata {
  name: string;
  description: string;
  version: string;
  category: 'decision' | 'dem' | 'routeDirection' | ...;
  toolGroup?: 'DOMAIN' | 'CONTEXT';
  
  // 新增：输入参数定义
  inputSchema?: {
    required?: string[]; // 必需参数列表
    optional?: string[]; // 可选参数列表
    dependencies?: Array<{
      param: string; // 参数名
      dependsOn: string[]; // 依赖的参数（如果这些参数缺失，该参数必需）
      alternatives?: string[]; // 替代参数（如果这些参数存在，该参数可选）
    }>;
    extractors?: Record<string, (context: any, request: any) => any>; // 参数提取器
  };
}
```

**2. 在 Skill 实现中定义验证规则**

```typescript
@Injectable()
export class DecisionRunThreeGuardiansSkill implements Skill {
  metadata = {
    name: 'decision.runThreeGuardians',
    description: '一次性执行三人格策略编排',
    version: '1.0.0',
    category: 'decision' as const,
    inputSchema: {
      required: [], // 没有绝对必需的参数
      dependencies: [
        {
          param: 'world',
          dependsOn: [],
          alternatives: ['tripId'], // world 或 tripId 至少需要一个
        },
        {
          param: 'tripId',
          dependsOn: [],
          alternatives: ['world'], // tripId 或 world 至少需要一个
        },
      ],
      extractors: {
        tripId: (context, request) => context.tripId || request.trip_id,
      },
    },
  };
  
  // ...
}
```

**3. 统一验证服务**

```typescript
@Injectable()
export class SkillInputValidatorService {
  /**
   * 验证 skill 输入参数
   */
  validateSkillInput(
    skill: Skill,
    input: any,
    context: AgentContext,
    request: RouteAndRunRequestDto,
  ): ValidationResult {
    const schema = skill.metadata.inputSchema;
    if (!schema) {
      return { valid: true }; // 没有定义 schema，跳过验证
    }
    
    const missingParams: string[] = [];
    
    // 1. 检查必需参数
    if (schema.required) {
      for (const param of schema.required) {
        if (!this.hasValue(input[param], context, request)) {
          missingParams.push(param);
        }
      }
    }
    
    // 2. 检查依赖关系
    if (schema.dependencies) {
      for (const dep of schema.dependencies) {
        const hasParam = this.hasValue(input[dep.param], context, request);
        const hasAlternatives = dep.alternatives?.some(alt => 
          this.hasValue(input[alt], context, request)
        );
        
        if (!hasParam && !hasAlternatives) {
          missingParams.push(`${dep.param} 或 ${dep.alternatives?.join('、')}`);
        }
      }
    }
    
    // 3. 使用提取器填充参数
    if (schema.extractors) {
      for (const [param, extractor] of Object.entries(schema.extractors)) {
        if (!input[param]) {
          const extracted = extractor(context, request);
          if (extracted) {
            input[param] = extracted;
          }
        }
      }
    }
    
    return {
      valid: missingParams.length === 0,
      missingParams,
    };
  }
  
  private hasValue(value: any, context: AgentContext, request: RouteAndRunRequestDto): boolean {
    if (value !== undefined && value !== null && value !== '') {
      return true;
    }
    return false;
  }
}
```

**4. 在 Skills 选择阶段进行验证**

```typescript
// 在 selectSkills 之后，立即验证
const skillsPlan = await this.selectSkills(intentAnalysis, routingDecision, context, llmProvider);

// 提前验证（在 plan 编排之前）
const validationResult = await this.validateSkillsInputs(skillsPlan, context, request);
if (!validationResult.valid) {
  return {
    success: false,
    result: {
      needsUserConfirmation: true,
      clarificationMessage: this.buildClarificationMessage(validationResult),
      // ...
    },
    // ...
  };
}
```

#### 优点

✅ **声明式**：验证规则定义在 skill metadata 中，清晰明确  
✅ **可扩展**：新增 skill 只需定义 metadata，无需修改验证逻辑  
✅ **统一**：所有 skill 使用统一的验证接口  
✅ **提前验证**：在 Skills 选择阶段就进行验证，节省 LLM 成本  
✅ **自动提取**：支持参数提取器，自动从 context/request 中提取参数  

#### 缺点

⚠️ **需要修改所有 skill**：需要为每个 skill 添加 inputSchema  
⚠️ **迁移成本**：需要逐步迁移现有 skill

### 方案 2：基于 TypeScript 类型自动提取（长期）

#### 核心思想

**从 TypeScript 接口自动提取必需参数**

#### 架构设计

**1. 使用装饰器定义验证规则**

```typescript
@RequiredParams(['world', 'tripId'], { alternatives: true }) // world 或 tripId 至少一个
export interface DecisionRunThreeGuardiansInput extends SkillInput {
  tripId?: string;
  world?: WorldModelContext;
  planCandidate: RoutePlanDraft;
}
```

**2. 使用反射提取验证规则**

```typescript
// 使用 TypeScript 编译时信息或运行时反射
const inputType = getType<DecisionRunThreeGuardiansInput>();
const requiredParams = extractRequiredParams(inputType);
```

#### 优点

✅ **类型安全**：利用 TypeScript 类型系统  
✅ **自动提取**：无需手动定义验证规则  
✅ **编译时检查**：编译时就能发现类型错误  

#### 缺点

⚠️ **技术复杂度高**：需要 TypeScript 反射或编译时工具  
⚠️ **运行时性能**：反射可能影响性能  
⚠️ **依赖关系处理**：复杂的依赖关系难以用类型系统表达

### 用户体验提升

- **响应速度**：更快返回澄清问题
- **准确性**：更准确的参数验证
- **覆盖度**：更高的验证覆盖率

## 📋 风险评估

### 风险 1：迁移成本

**风险**：需要为所有 skill 添加 inputSchema  
**缓解**：采用渐进式迁移，先迁移核心 skill，再逐步迁移其他 skill  

### 风险 2：验证准确性

**风险**：验证逻辑可能与实际执行时的逻辑不一致  
**缓解**：添加集成测试，验证验证逻辑的准确性  

### 风险 3：性能影响

**风险**：验证逻辑可能影响性能  
**缓解**：优化验证逻辑，使用缓存，并行验证
