## 0.1 项目背景与问题定义（Why Now）

### 背景：TripNARA AI架构现状

TripNARA 作为**决策型旅行应用**，采用多智能体系统架构，通过 **CLAUDE_SM 状态机编排**（8步流程）完成复杂的行程规划任务。系统当前支持**4个LLM提供商**（Claude、OpenAI、DeepSeek、Gemini），具备完善的降级机制和性能监控体系。

**参考架构文档**：
- `docs/AGENT_ARCHITECTURE_LATEST.md` - 最新架构文档
- `.claude/改动资料/首席AI科学家-评估-TripNARA架构评估-2025-01-14.md` - 架构评估报告

### 当前成本压力与性能瓶颈

#### 1. LLM调用成本高

**问题描述**：
- **现状**：所有任务都使用相同的默认LLM提供商（当前优先DeepSeek），无法根据任务特性选择最优模型
- **影响**：
  - 简单任务（如实体解析）使用高成本模型，造成浪费
  - 复杂推理任务可能使用能力不足的模型，导致重试和额外成本
  - **预估成本浪费**：30-50%

**代码证据**：
```typescript
// src/llm/services/llm.service.ts:80-96
// 当前实现：根据API Key配置选择默认提供商，所有任务使用相同提供商
if (deepseekKey) {
  this.defaultProvider = LlmProvider.DEEPSEEK;
} else if (openaiKey) {
  this.defaultProvider = LlmProvider.OPENAI;
}
// 缺少基于任务类型的智能路由
```

#### 2. 成本透明度缺失

**问题描述**：
- **现状**：有Token预算追踪（`TelemetryService`），但缺少详细的Token使用统计和实际成本计算
- **影响**：
  - 无法分析哪些Sub-Agent消耗Token最多
  - 无法识别成本优化机会
  - 无法设置成本告警和预算控制
  - **管理盲区**：成本黑盒，无法数据驱动优化

**代码证据**：
```typescript
// src/agent/infra/telemetry.service.ts:39-50
// 当前实现：有Token追踪，但缺少统计和分析
export interface PerformanceMetrics {
  llmTokens?: {
    prompt: number;
    completion: number;
    total: number;
  };
}
// 缺少：Sub-Agent级别统计、任务类型级别统计、成本计算
```

#### 3. RESEARCH步骤性能瓶颈

**问题描述**：
- **现状**：RESEARCH步骤中多个Skills（transport.search、poi.search、opening_hours.get、dem.get.profile等）可能串行执行
- **影响**：
  - RESEARCH步骤延迟高，影响整体响应时间
  - 独立Skills无法并行执行，浪费等待时间
  - **预估性能损失**：40-60%延迟增加

### 架构评估发现的核心问题

根据**首席AI科学家的架构评估报告**（2025-01-14），发现以下**P0优先级问题**：

#### 问题1：缺少模型路由策略 ⚠️ **P0**

**评估结论**：
- **成熟度**：技术成熟，有生产案例（OpenAI、Anthropic都有类似实现）
- **适用性**：非常适合TripNARA场景，可以显著降低成本
- **实施复杂度**：中等（需要定义路由规则、实现路由逻辑）
- **预期收益**：成本降低30-50%

#### 问题2：缺少Token使用统计 ⚠️ **P0**

**评估结论**：
- **成熟度**：技术成熟，TelemetryService已有基础
- **适用性**：必需功能，成本优化的前提
- **实施复杂度**：低（扩展现有TelemetryService）
- **预期收益**：成本透明度提升，优化方向明确

#### 问题3：缺少成本计算 ⚠️ **P0**

**评估结论**：
- **成熟度**：技术成熟，基于Token使用和API定价计算
- **适用性**：必需功能，成本控制的前提
- **实施复杂度**：中等（需要API定价配置、成本计算逻辑）
- **预期收益**：成本透明度提升，成本控制能力增强

#### 问题4：RESEARCH步骤串行执行 ⚠️ **P0**

**评估结论**：
- **成熟度**：技术成熟，并行执行是常见优化手段
- **适用性**：非常适合，RESEARCH步骤中Skills相互独立
- **实施复杂度**：中等（需要依赖分析、并行执行框架）
- **预期收益**：延迟降低40-60%

### 为什么现在必须解决（Why Now）

#### 1. 成本压力日益增大

**现状**：
- LLM API调用成本随着使用量增长而线性增长
- 当前缺少成本优化手段，成本不可控
- **如果不优化**：随着用户增长，成本将快速增长，影响业务可持续性

**紧迫性**：**高** - 成本优化是业务可持续性的基础

#### 2. 性能瓶颈影响用户体验

**现状**：
- RESEARCH步骤串行执行导致延迟高
- 用户等待时间长，影响体验
- **如果不优化**：随着复杂度增加，延迟将进一步恶化

**紧迫性**：**高** - 性能优化直接影响用户体验

#### 3. 缺少数据驱动决策能力

**现状**：
- 缺少Token使用统计，无法分析成本分布
- 缺少成本计算，无法设置预算和告警
- **如果不优化**：无法数据驱动优化，优化方向不明确

**紧迫性**：**中** - 数据驱动是持续优化的基础

#### 4. 架构评估已识别问题

**现状**：
- 首席AI科学家已完成架构评估，识别了P0优先级问题
- 技术方案清晰，实施路径明确
- **如果不优化**：错失优化窗口，技术债务积累

**紧迫性**：**高** - 问题已识别，方案已明确，应该立即实施

### 边界与异常

#### 功能边界

**包含**：
- ✅ 模型路由策略实现
- ✅ Token使用统计实现
- ✅ 成本计算实现
- ✅ RESEARCH步骤并行执行优化

**不包含**：
- ❌ 不改变现有API接口（`POST /agent/route_and_run`保持兼容）
- ❌ 不改变现有Sub-Agents逻辑（只优化调用方式）
- ❌ 不涉及前端UI（纯后端优化）
- ❌ 不涉及RAG系统优化（P1优先级）
- ❌ 不涉及提示工程优化（P1优先级）

#### 异常处理

**模型路由失败**：
- **降级策略**：路由失败时使用默认提供商
- **日志记录**：记录路由失败原因，用于问题排查
- **监控告警**：路由失败率超过阈值时告警

**Token统计失败**：
- **降级策略**：统计失败不影响主流程，记录警告日志
- **数据补偿**：统计失败时使用估算值
- **监控告警**：统计失败率超过阈值时告警

**成本计算失败**：
- **降级策略**：计算失败时返回估算成本
- **数据补偿**：使用历史平均成本作为估算
- **监控告警**：计算失败率超过阈值时告警

**并行执行失败**：
- **降级策略**：并行执行失败时降级到串行执行
- **日志记录**：记录并行执行失败原因
- **监控告警**：并行执行失败率超过阈值时告警

#### 定义

**总体成本降低率**：实施优化后，LLM调用成本相对于基线的降低比例

**计算公式**：
```
总体成本降低率 = (基线成本 - 优化后成本) / 基线成本 × 100%
```

**基线定义**：
- **基线成本**：优化前30天的平均每日LLM调用成本
- **优化后成本**：优化后30天的平均每日LLM调用成本
- **成本计算**：基于Token消耗和API定价（参考各LLM提供商的定价）

#### 目标值

**主要目标**：**总体成本降低40-60%**

**分解目标**：
- **模型路由策略**：贡献成本降低30-50%
- **Token统计与成本计算**：贡献成本透明度提升（间接优化）
- **并行执行优化**：贡献延迟降低（间接优化成本，通过减少重试）

#### 为什么选择这个指标

1. **直接反映核心价值**：成本优化是本项目的核心目标
2. **可量化**：成本数据可以精确计算和追踪

### 边界与异常

#### 指标边界

**成本降低边界**：
- **上限**：成本降低不应超过70%（过度优化可能影响质量）
- **下限**：成本降低不应低于30%（未达到预期目标）
- **异常处理**：成本降低异常时（如成本反而增加），需要立即回滚

**延迟降低边界**：
- **上限**：延迟降低不应超过80%（过度优化可能影响稳定性）
- **下限**：延迟降低不应低于20%（未达到预期目标）
- **异常处理**：延迟降低异常时（如延迟反而增加），需要立即回滚

**准确率边界**：
- **路由准确率**：不应低于85%（低于此值需要调整路由规则）
- **成本计算准确率**：不应低于90%（低于此值需要检查定价配置）
- **异常处理**：准确率异常时，需要分析原因并修复

#### 异常情况处理

**成本降低异常**：
- **现象**：成本反而增加或降低幅度<20%
- **处理**：立即回滚优化，分析原因，修复后重新上线
- **监控**：设置成本告警阈值（成本增加>10%时告警）

**延迟降低异常**：
- **现象**：延迟反而增加或降低幅度<20%
- **处理**：立即回滚优化，分析原因，修复后重新上线
- **监控**：设置延迟告警阈值（延迟增加>20%时告警）

**准确率异常**：
- **现象**：路由准确率<85%或成本计算准确率<90%
- **处理**：分析原因，调整路由规则或定价配置
- **监控**：设置准确率告警阈值（准确率低于阈值时告警）

### 边界与异常

#### 用户权限边界

**内部用户**（AI工程师、架构师、运维团队）：
- ✅ 可以查看Token统计和成本数据
- ✅ 可以配置模型路由规则
- ✅ 可以设置成本告警
- ✅ 可以查看性能监控数据

**外部用户**（最终用户）：
- ❌ 不能查看Token统计和成本数据（内部数据）
- ❌ 不能配置模型路由规则（系统自动路由）
- ✅ 间接受益于性能提升和成本降低

#### 异常场景处理

**场景1：Token统计失败**
- **现象**：Token统计功能异常，无法统计Token使用
- **影响**：成本透明度降低，无法分析成本分布
- **处理**：降级处理，记录警告日志，不影响主流程
- **恢复**：修复统计功能，补偿统计数据

**场景2：成本计算失败**
- **现象**：成本计算功能异常，无法计算成本
- **影响**：成本透明度降低，无法设置成本告警
- **处理**：降级处理，使用估算成本，记录警告日志
- **恢复**：修复计算功能，补偿成本数据

**场景3：模型路由失败**
- **现象**：模型路由功能异常，无法选择最优模型
- **影响**：成本优化失效，可能使用高成本模型
- **处理**：降级到默认提供商，记录警告日志
- **恢复**：修复路由功能，恢复正常路由

**场景4：并行执行失败**
- **现象**：并行执行功能异常，无法并行执行Skills
- **影响**：性能优化失效，延迟可能增加
- **处理**：降级到串行执行，记录警告日志
- **恢复**：修复并行执行功能，恢复正常并行执行

### 数据流：端到端闭环

#### 阶段1：请求输入与路由决策

**输入**：
- 用户请求：`RouteAndRunRequestDto`
- 任务类型：从请求中识别（实体解析、Gate评估、行程生成等）

**流程**：
```
用户请求
    ↓
任务类型识别（PlannerAgent）
    ↓
模型路由策略（ModelRoutingService）
    ├─ 任务类型 → 推荐模型
    ├─ 路由决策 → 选择模型
    └─ 降级策略 → 备用模型
    ↓
LLM调用（LlmService）
    ├─ 使用选择的模型
    ├─ 记录Token使用
    └─ 返回结果
```

**输出**：
- 路由决策：`RoutingDecision`（选择的模型、理由、置信度）
- LLM响应：Sub-Agent的执行结果

**参考文件**：
- `src/agent/services/claude-orchestrator.service.ts` - Claude编排器
- `src/llm/services/llm.service.ts` - LLM服务

#### 阶段2：Token使用统计

**输入**：
- LLM调用结果：Token消耗（prompt、completion、total）
- 请求上下文：Sub-Agent、任务类型、提供商

**流程**：
```
LLM调用完成
    ↓
Token统计服务（TokenStatsService）
    ├─ 记录Token使用（Sub-Agent级别）
    ├─ 记录任务类型
    ├─ 记录提供商
    └─ 记录时间戳
    ↓
统计聚合（TokenStatsAggregator）
    ├─ 按Sub-Agent聚合
    ├─ 按任务类型聚合
    ├─ 按时间维度聚合
    └─ 生成统计报告
    ↓
数据存储（内存或持久化）
```

**输出**：
- Token使用统计：`TokenUsageStats`（每个请求的统计）
- 统计聚合：`TokenUsageAggregation`（聚合后的统计）

**参考文件**：
- `src/agent/infra/telemetry.service.ts` - Telemetry服务（需要扩展）

#### 阶段3：成本计算

**输入**：
- Token使用统计：`TokenUsageStats`
- API定价配置：`CostCalculationConfig`

**流程**：
```
Token使用统计
    ↓
成本计算服务（CostCalculationService）
    ├─ 读取API定价配置
    ├─ 计算Prompt成本（prompt_tokens × pricing.prompt_tokens_per_1k）
    ├─ 计算Completion成本（completion_tokens × pricing.completion_tokens_per_1k）
    └─ 计算总成本（prompt_cost + completion_cost）
    ↓
成本聚合（CostAggregator）
    ├─ 按请求聚合
    ├─ 按Sub-Agent聚合
    ├─ 按时间维度聚合
    └─ 生成成本报告
    ↓
成本告警（CostAlertService）
    ├─ 检查成本阈值
    ├─ 发送告警通知
    └─ 记录告警事件
```

**输出**：
- 成本计算结果：`CostCalculation`（每个请求的成本）
- 成本聚合：`CostAggregation`（聚合后的成本）
- 成本告警：`CostAlert`（如需要）

**参考文件**：
- 新增：`src/agent/services/cost-calculation.service.ts`（待实现）

#### 阶段4：并行执行优化

**输入**：

**流程**：
```

依赖分析服务（DependencyAnalyzerService）
    ├─ 分析Skills依赖关系
    ├─ 识别独立Skills（可并行）
    └─ 识别依赖Skills（需串行）

    ├─ 依赖Skills串行执行
    └─ 监控执行状态
    ↓

    ├─ 记录并行执行时间
    ├─ 记录串行预估时间
    ├─ 计算加速比
    └─ 记录性能指标
```

**输出**：
- 并行执行结果：`ParallelExecutionResult`（执行的Skills、加速比、性能指标）

#### 阶段5：反馈闭环

**输入**：
- 成本数据：`CostCalculation`
- 性能数据：`ParallelExecutionResult`
- Token统计：`TokenUsageStats`

**流程**：
```
数据收集
    ↓
数据分析服务（AnalyticsService）
    ├─ 分析成本分布（哪些Sub-Agent成本高）
    ├─ 分析性能瓶颈（哪些步骤延迟高）
    ├─ 分析Token消耗（哪些任务消耗Token多）
    └─ 识别优化机会
    ↓
优化决策（OptimizationDecisionService）
    ├─ 调整模型路由规则（如简单任务→DeepSeek）
    ├─ 调整并行执行策略（如增加并行数）
    ├─ 调整成本告警阈值
    └─ 生成优化建议
    ↓
效果验证（EffectivenessValidator）
    ├─ 验证成本降低效果
    ├─ 验证性能提升效果
    └─ 验证质量保持（不影响功能）
    ↓
持续优化（ContinuousOptimization）
    ├─ 根据数据持续调整
    └─ 形成优化闭环
```

**输出**：
- 分析报告：`AnalyticsReport`（成本分析、性能分析、优化建议）
- 优化决策：`OptimizationDecision`（路由规则调整、并行策略调整）
- 效果验证：`EffectivenessValidation`（成本降低、性能提升、质量保持）

### 边界与异常

#### 数据流边界

**模型路由边界**：
- **输入边界**：只处理LLM调用请求
- **输出边界**：只输出路由决策，不修改请求内容
- **异常处理**：路由失败时降级到默认提供商

**Token统计边界**：
- **输入边界**：只统计LLM调用的Token使用
- **输出边界**：只输出统计结果，不修改LLM调用
- **异常处理**：统计失败时记录警告，不影响主流程

**成本计算边界**：
- **输入边界**：只计算LLM调用的成本
- **输出边界**：只输出成本计算结果，不修改Token统计
- **异常处理**：计算失败时使用估算成本

**并行执行边界**：
- **输入边界**：只优化RESEARCH步骤的Skills执行
- **输出边界**：只优化执行方式，不修改Skills逻辑
- **异常处理**：并行执行失败时降级到串行执行

#### 异常情况处理

**数据流中断**：
- **现象**：某个阶段失败，数据流中断
- **处理**：降级处理，记录警告日志，不影响主流程
- **恢复**：修复失败阶段，恢复数据流

**数据不一致**：
- **现象**：Token统计和成本计算数据不一致
- **处理**：使用最新数据，记录不一致警告
- **恢复**：修复数据不一致问题

## 0.7 关键流程（用户流 + 系统流 + 异常流）

### 编排模式说明

**使用的编排模式**：**CLAUDE_SM**（Claude状态机编排）

**选择原因**：
- 4个P0项目主要影响LLM调用和RESEARCH步骤
- CLAUDE_SM模式提供结构化的8步状态机流程
- 便于在特定步骤集成成本优化和性能优化功能

**状态机流程**（8步严格顺序）：
```
INTAKE → RESEARCH → GATE_EVAL → PLAN_GEN → VERIFY → REPAIR → NARRATE → DONE
```

**4个P0项目的集成点**：
- **项目1（模型路由策略）**：集成在LLM调用之前（所有Sub-Agent调用LLM时）
- **项目2（Token使用统计）**：集成在LLM调用之后（所有Sub-Agent调用LLM后）
- **项目3（成本计算）**：集成在Token统计之后（异步计算）
- **项目4（并行执行优化）**：集成在RESEARCH步骤（Skills并行执行）

#### 异常流1：模型路由失败

**场景**：模型路由策略无法选择模型

**流程**：
```
模型路由策略执行
    ↓
路由决策失败（如配置错误、模型不可用）
    ↓
[降级处理]
    ├─ 1. 使用默认提供商
    │  └─ 调用LlmService.getDefaultProvider()
    ↓
    ├─ 2. 记录路由失败事件
    │  ├─ 记录失败原因
    │  ├─ 记录使用的降级模型
    │  └─ 记录时间戳
    ↓
    └─ 3. 继续执行（不影响主流程）
        └─ 使用降级模型调用LLM
```

**处理策略**：
- **降级**：使用默认提供商
- **记录**：记录路由失败事件
- **告警**：发送路由失败告警（如需要）

**影响范围**：
- 不影响主流程（继续执行）
- 可能影响成本（使用非最优模型）
- 可能影响性能（使用非最优模型）

```
    └─ 3. 继续执行（不影响主流程）
        └─ 使用串行执行结果，继续后续步骤
```

**处理策略**：
- **降级**：降级到串行执行
- **记录**：记录并行执行失败事件
- **告警**：发送并行执行失败告警（如需要）

**影响范围**：
- 不影响主流程（继续执行）
- 影响性能（延迟增加，无并行加速）
- 影响用户体验（响应时间变慢）

#### 异常流5：LLM调用失败（与成本优化相关）

**场景**：LLM调用失败，触发降级和重试

**流程**：
```

    ↓

    ↓
    ├─ 2. 降级到备用模型/提供商
    │  ├─ 使用备用模型重试
    │  └─ 记录降级事件
    ↓

    │  ├─ 使用指数退避重试
    │  └─ 记录重试次数
    ↓

        ├─ 记录失败事件
        ├─ 记录Token使用（如已消耗）
        └─ 返回错误结果
```

**处理策略**：
- **降级**：降级到备用模型/提供商
- **重试**：使用指数退避重试
- **记录**：记录降级和失败事件

**影响范围**：
- 可能影响主流程（如最终失败）
- 影响成本（可能使用更昂贵的备用模型）
- 影响性能（重试增加延迟）

## 0.8 核心能力1：模型路由策略（智能模型选择）

### 功能概述

**目标**：根据任务类型、复杂度、成本等因素，智能选择最适合的LLM模型，实现成本降低40-60%的目标。

**核心价值**：
- **成本优化**：简单任务使用低成本模型（DeepSeek），复杂任务使用高性能模型（Claude）
- **性能平衡**：在成本和性能之间找到最佳平衡点
- **透明度**：记录路由决策，便于分析和优化

#### 任务复杂度评估

**复杂度评估维度**：

1. **输入长度**：
   - 低复杂度：< 1000 tokens
   - 中复杂度：1000-5000 tokens
   - 高复杂度：> 5000 tokens

2. **推理深度**：
   - 低复杂度：简单规则匹配、文本解析
   - 中复杂度：简单推理、规则+少量推理
   - 高复杂度：复杂推理、多步骤推理、创造性生成

3. **输出复杂度**：
   - 低复杂度：简单文本、结构化数据（简单）
   - 中复杂度：结构化数据（复杂）、多段落文本
   - 高复杂度：复杂结构化数据、长文本生成

4. **风险等级**：
   - 低风险：文本生成、简单解析
   - 中风险：规则验证、简单决策
   - 高风险：Gate评估、安全决策、关键规划

**复杂度评估算法**：

```typescript
function assessTaskComplexity(
  subAgent: SubAgentType,
  step: OrchestrationStep,
  context: AgentContext
): 'low' | 'medium' | 'high' {
  let complexityScore = 0;
  
  // 基于Sub-Agent的复杂度
  const agentComplexity = {
    'PlannerAgent': 2, // 中-高
    'GatekeeperAgent': 3, // 高
    'CoreDecisionAgent': 2, // 中-高
    'LocalInsightAgent': 3, // 高
    'ComplianceAgent': 1, // 低-中
    'NarratorAgent': 1, // 低-中
  };
  complexityScore += agentComplexity[subAgent] || 1;
  
  // 基于状态机步骤的复杂度
  const stepComplexity = {
    'INTAKE': 1, // 低
    'RESEARCH': 0, // 不涉及LLM
    'GATE_EVAL': 3, // 高
    'PLAN_GEN': 3, // 高
    'VERIFY': 2, // 中
    'REPAIR': 3, // 高
    'NARRATE': 1, // 低
  };
  complexityScore += stepComplexity[step] || 1;
  
  // 基于上下文的复杂度
  if (context.input_length > 5000) complexityScore += 1;
  if (context.requires_reasoning) complexityScore += 1;
  if (context.risk_level === 'high') complexityScore += 1;
  
  // 综合评估
  if (complexityScore >= 5) return 'high';
  if (complexityScore >= 3) return 'medium';
  return 'low';
}
```

### 降级策略

#### 降级场景

**场景1：主模型不可用**

**触发条件**：
- API Key未配置
- 熔断器打开（连续失败）
- 模型服务不可用

**降级流程**：
```
主模型不可用
    ↓
检查降级策略（fallback_providers）
    ↓
按顺序尝试降级模型
    ├─ 尝试第一个降级模型
    ├─ 如果失败，尝试第二个降级模型
    └─ 如果都失败，使用默认模型
    ↓
记录降级事件
    ├─ 记录降级原因
    ├─ 记录使用的降级模型
    └─ 记录时间戳
    ↓
使用降级模型调用LLM
```

**场景2：主模型调用失败**

**触发条件**：
- 网络错误
- API错误（4xx/5xx）
- 超时错误

**降级流程**：
```
主模型调用失败
    ↓
检查错误类型
    ├─ 网络错误 → 重试 + 降级
    ├─ API错误（4xx） → 直接降级（不重试）
    └─ API错误（5xx） → 重试 + 降级
    ↓
重试机制（如适用）
    ├─ 指数退避重试（最多3次）
    └─ 如果重试失败，降级
    ↓
降级到备用模型
    ├─ 使用降级策略
    └─ 记录降级事件
    ↓
使用降级模型调用LLM
```

**场景3：成本超限**

**触发条件**：
- 累计成本超过阈值
- 单次请求成本超过阈值

**降级流程**：
```
成本超限检测
    ↓
检查成本阈值
    ├─ 累计成本 > 阈值 → 强制使用低成本模型
    └─ 单次请求成本 > 阈值 → 警告 + 建议降级
    ↓
强制降级到低成本模型（DeepSeek）
    ├─ 忽略路由规则
    ├─ 使用DeepSeek
    └─ 记录成本超限事件
    ↓
使用低成本模型调用LLM
```

#### 降级优先级

**降级优先级规则**：

1. **用户指定优先**：如果用户指定了provider，优先使用（除非不可用）
2. **成本优先**：在可用模型中，优先选择低成本模型
3. **性能优先**：在成本相近时，优先选择高性能模型
4. **默认模型**：如果所有模型都不可用，使用系统默认模型

#### 集成点1：LLM服务集成

**集成方式**：

```typescript
// src/llm/services/llm.service.ts
async callLlm(
  provider: LlmProvider,
  prompt: string,
  schema?: any
): Promise<string> {
  const startTime = Date.now();
  const traceId = this.getCurrentTraceId();
  const spanId = this.getCurrentSpanId();
  
  try {
    // 调用LLM
    const response = await this.callLlmInternal(provider, prompt, schema);
    
    // 提取Token使用（从响应中）
    const tokenUsage = this.extractTokenUsage(response, provider);
    
    // 记录Token使用
    if (this.tokenStatsService) {
      await this.tokenStatsService.recordTokenUsage({
        request_id: this.getCurrentRequestId(),
        trace_id: traceId,
        span_id: spanId,
        sub_agent: this.getCurrentSubAgent(),
        state_machine_step: this.getCurrentStep(),
        task_type: this.getCurrentTaskType(),
        provider,
        model: this.getModelName(provider),
        prompt_tokens: tokenUsage.prompt_tokens,
        completion_tokens: tokenUsage.completion_tokens,
        total_tokens: tokenUsage.total_tokens,
        duration_ms: Date.now() - startTime,
        success: true,
        timestamp: new Date().toISOString(),
      });
    }
    
    return response;
  } catch (error) {
    // 记录失败
    if (this.tokenStatsService) {
      await this.tokenStatsService.recordTokenUsage({
        // ... 失败记录
        success: false,
        error: error.message,
      });
```

### 边界与异常

#### 功能边界

**Token统计边界**：
- **输入边界**：只统计LLM调用的Token使用，不统计其他操作
- **输出边界**：只输出统计结果，不修改LLM调用
- **影响范围**：不影响主流程，只记录数据

**不支持的场景**：

**现象**：无法从LLM响应中提取Token使用数据

**处理**：
- 使用估算值（基于字符数估算）
- 记录警告日志
- 继续执行（不影响主流程）

- 降级到内存存储

**处理**：

#### 成本计算公式

**单次LLM调用成本**：

```
成本 = (Prompt Tokens / 1000) × Prompt定价 + (Completion Tokens / 1000) × Completion定价
```

**示例计算**：

```
场景：使用Claude 3.5 Sonnet生成行程
- Prompt Tokens: 2000
- Completion Tokens: 1500
- Prompt定价: $0.003 per 1K tokens
- Completion定价: $0.015 per 1K tokens

成本计算：
= (2000 / 1000) × 0.003 + (1500 / 1000) × 0.015
= 2 × 0.003 + 1.5 × 0.015
= 0.006 + 0.0225
= $0.0285
```

**成本计算数据结构**：

### 成本告警设计

#### 告警规则

**规则1：单次请求成本告警**

**告警内容**：

- 高成本调用详情

**规则2：累计成本告警**

**触发条件**：
- 累计成本（小时/天/周/月）> 阈值（如 $100/天）

**告警内容**：
- 时间范围
- 累计成本
- 成本趋势
- 成本分布

**规则3：成本异常告警**

**触发条件**：
- 成本突然增加（如相比前一天增加50%）
- 某个Sub-Agent成本异常高

**告警内容**：
- 异常类型
- 异常详情
- 建议优化措施

## 0.11 核心能力4：并行执行优化（RESEARCH步骤性能提升）

### 功能概述

**目标**：优化RESEARCH步骤的Skills执行方式，通过并行执行独立Skills，将RESEARCH步骤延迟降低40-60%。

**核心价值**：
- **性能提升**：并行执行独立Skills，大幅降低RESEARCH步骤延迟
- **用户体验**：更快的响应时间，提升用户体验
- **资源利用**：充分利用系统资源，提高吞吐量

---

### 当前实现分析

#### 当前执行方式

**现状**：RESEARCH步骤中的Skills是**串行执行**的

**当前代码**（`claude-orchestrator.service.ts:2369-2570`）：

```typescript
// 当前实现：串行执行
// 1. 交通搜索
const transportResult = await transportSkill.execute({...});

// 2. POI搜索（依赖transport完成）
const poiResult = await poiSkill.execute({...});

// 3. 开放时间查询（依赖poi完成）
const openingHoursResult = await openingHoursSkill.execute({...});

// 4. DEM指标（独立）
const demResult = await demSkill.execute({...});

// 5. 风险检查（独立）
const riskResult = await riskSkill.execute({...});
```

**问题**：
- 所有Skills串行执行，总延迟 = 各Skills延迟之和
- 独立Skills（如transport、poi、dem、risk）可以并行执行
- 预估延迟：如果每个Skill平均500ms，5个Skills串行 = 2500ms

#### 优化机会识别

**独立Skills（可并行）**：
- `transport.search` - 交通搜索（独立）
- `poi.search` - POI搜索（独立）
- `dem.get.profile` - DEM指标（独立）
- `geo.check.hazard.zones` - 风险检查（独立）

**依赖Skills（需串行）**：
- `opening_hours.get` - 开放时间查询（依赖`poi.search`的结果）

**优化方案**：
- 独立Skills并行执行（使用`Promise.all`）
- 依赖Skills在依赖完成后执行
- 预估延迟：并行执行4个独立Skills（取最慢的，约500ms）+ 串行执行1个依赖Skill（约500ms）= 1000ms
- **性能提升**：从2500ms降低到1000ms，**提升60%**

#### 并行执行实现

**实现代码**：

```typescript
async executeParallel(
  executionPlan: ExecutionPlan,
  context: ExecutionContext
): Promise<ParallelExecutionResult> {
  const startTime = Date.now();
  const results: Record<string, SkillExecutionResult> = {};
  const errors: Record<string, Error> = {};
  
  // 按顺序执行并行组
  for (const groupId of executionPlan.execution_order) {
    const group = executionPlan.parallel_groups.find(g => g.group_id === groupId);
    if (!group) continue;
    
    // 并行执行组内的Skills
    const groupResults = await Promise.allSettled(
      group.skills.map(skillName => 
        this.executeSkill(skillName, context.inputs[skillName], context.timeouts[skillName])
      )
    );
    
    // 处理结果
    groupResults.forEach((result, index) => {
      const skillName = group.skills[index];
      if (result.status === 'fulfilled') {
        results[skillName] = result.value;
      } else {
        errors[skillName] = result.reason;
      }
    });
    
    // 如果有关键Skill失败，决定是否继续
    const criticalFailures = group.skills.filter(
      skillName => 
        context.criticalSkills.includes(skillName) && 
        errors[skillName]
    );
    
    if (criticalFailures.length > 0) {
      // 根据失败策略决定是否继续
      if (context.failureStrategy === 'abort') {
        throw new Error(`关键Skill失败: ${criticalFailures.join(', ')}`);
      }
    }
  }
  
  const totalDuration = Date.now() - startTime;
  
  return {
    success: Object.keys(errors).length === 0,
    results,
    errors,
    duration_ms: totalDuration,
    estimated_serial_duration_ms: executionPlan.estimated_serial_duration_ms,
    speedup_ratio: executionPlan.estimated_serial_duration_ms / totalDuration,
  };
}
```

**场景**：非关键Skills失败，关键Skills成功

**处理**：
- 记录失败Skills
- 继续执行后续Skills
- 返回部分结果（标记缺失的Skills）

**策略2：关键失败降级**

**场景**：关键Skills失败

**处理**：
- 如果失败策略 = 'abort' → 抛出错误，停止执行
- 如果失败策略 = 'degrade' → 标记缺失，继续执行
- 如果失败策略 = 'retry' → 重试失败Skills

**策略3：超时处理**

**场景**：Skill执行超时

**处理**：
- 取消超时Skill的执行
- 记录超时事件
- 根据失败策略决定是否继续

#### 集成点1：RESEARCH步骤集成

**位置**：`ClaudeOrchestratorService.executeResearchStep()`

**集成方式**：

```typescript
private async executeResearchStep(
  request: RouteAndRunRequestDto,
  context: AgentContext,
  state: OrchestratorState,
  provider: LlmProvider,
): Promise<void> {
  state.current_step = 'RESEARCH';
  const stepStartTime = Date.now();
  
  try {
    // 1. 确定需要执行的Skills
    const requiredSkills = this.determineRequiredSkills(state.trip_plan_request);
    
    // 2. 依赖分析
    const executionPlan = await this.dependencyAnalyzer.analyzeDependencies(requiredSkills);
    
    // 3. 并行执行
    const executionContext: ExecutionContext = {
      inputs: this.prepareSkillInputs(state.trip_plan_request),
      timeouts: this.getSkillTimeouts(),
      criticalSkills: ['transport.search', 'poi.search'],
      failureStrategy: 'degrade',
    };
    
    const parallelResult = await this.parallelExecutionService.executeParallel(
      executionPlan,
      executionContext
    );
    
    // 4. 处理结果
    const researchData = this.processExecutionResults(parallelResult.results);
    const evidenceRefs = this.extractEvidenceRefs(parallelResult.results);
    
    // 5. 更新状态
    state.research_data = researchData;
    state.evidence_registry = evidenceRefs;
    
    // 6. 记录性能指标
    state.metadata.research_metrics = {
      duration_ms: Date.now() - stepStartTime,
      parallel_duration_ms: parallelResult.duration_ms,
      estimated_serial_duration_ms: parallelResult.estimated_serial_duration_ms,
      speedup_ratio: parallelResult.speedup_ratio,
      skills_executed: Object.keys(parallelResult.results),
      skills_failed: Object.keys(parallelResult.errors),
    };
    
    // 7. 记录决策日志
    state.decision_log.push({
      request_id: state.request_id,
      step: 'RESEARCH',
      actor: 'Orchestrator',
      inputs_summary: `Skills: ${requiredSkills.join(', ')}`,
      outputs_summary: `并行执行完成，加速比: ${parallelResult.speedup_ratio.toFixed(2)}x`,
      evidence_refs: evidenceRefs,
      timestamp: new Date().toISOString(),
      metadata: {
        duration_ms: Date.now() - stepStartTime,
        parallel_execution: true,
        speedup_ratio: parallelResult.speedup_ratio,
      },
    });
    
  } catch (error: any) {
    this.logger.error(`[Claude Orchestrator] RESEARCH 步骤失败: ${error?.message}`);
    throw error;
  }
}
```

**容灾原则**：
- **不影响主流程**：所有P0项目的失败都不影响主流程
- **优雅降级**：失败时自动降级到备用方案
- **记录完整**：所有失败都记录日志，便于排查

**容灾措施**：
- **服务隔离**：P0项目服务独立，不影响核心服务
- **超时控制**：所有操作都有超时控制
- **重试机制**：关键操作支持重试（如需要）

## 0.17 风控、合规与责任边界（提示、免责声明、人工兜底）

### 技术风险

#### 风险1：模型路由错误

**风险描述**：路由决策错误，选择了不合适的模型

**影响**：
- 成本增加（选择了高成本模型）
- 性能下降（选择了低性能模型）
- 质量下降（选择了能力不足的模型）

**缓解措施**：
- 路由规则充分测试
- 路由决策记录完整
- 支持手动覆盖路由规则

#### 风险2：Token统计不准确

**风险描述**：Token统计数据不准确

**影响**：
- 成本分析不准确
- 优化决策错误

**缓解措施**：
- 数据校验机制
- 统计失败时记录警告
- 支持数据修正

#### 风险3：成本计算不准确

**风险描述**：成本计算结果不准确

**影响**：
- 成本报告不准确
- 预算控制失效

**缓解措施**：
- 定价配置定期更新
- 成本计算校验
- 支持成本修正

#### 风险4：并行执行失败

**风险描述**：并行执行失败，降级到串行

**影响**：
- 性能回退
- 用户体验下降

**缓解措施**：
- 完善的错误处理
- 自动降级到串行
- 性能监控告警

**数据范围**：
- Token使用统计：不涉及用户隐私数据

- 数据加密存储（如需要）

- ✅ 提供数据统计功能
