# 提前验证参数优化 - 多角色会审报告

**会审日期**: 2025-01-14  
**会审角色**: 智能体工程师、架构师、后端工程师  
**优化内容**: 在执行 plan 之前添加参数验证，提前识别缺失参数并返回澄清问题

---

## 📋 优化背景

### 问题描述

**用户反馈**：
> "需要用户澄清的内容能不能早点提供而不是等到超时了报错"

**当前问题**：
- 系统在执行 skill 时才发现缺jia
- 需要等待 skill 执行失败（可能超时）后才返回澄清问题
- 用户体验差，浪费时间和资源

**优化目标**：
- 在执行 plan 之前就识别出缺少的参数
- 提前返回澄清问题，避免执行可能失败的 skills
- 节省时间和资源，提升用户体验

---

## 🔍 智能体工程师评审

### 技术实现分析

**实现方案**：
1. 新增 `validatePlanInputs` 方法，在执行 plan 之前验证所有 skill 的必需参数
2. 集成到编排流程中，作为步骤 5.5/6（在执行 plan 之前）
3. 如果验证失败，立即返回澄清问题，不执行 plan

**验证规则**：
```typescript
// decision.runThreeGuardians: 需要 world 或 tripId
if (step.skillName === 'decision.runThreeGuardians') {
  if (!input.world && !input.tripId && !actualTripId) {
    missingParams.push('world 或 tripId');
  }
}

// world.buildContext: 需要 countryCode 或 tripId
if (step.skillName === 'world.buildContext') {
  if (!input.tripId && !input.countryCode && !actualTripId) {
    const countryCode = this.extractCountryCodeFromMessage(request.message);
    if (!countryCode) {
      missingParams.push('countryCode 或 tripId');
    }
  }
}

// routeDirection.pickForIntent: 需要 countryCode
if (step.skillName === 'routeDirection.pickForIntent') {
  if (!input.countryCode) {
    const countryCode = this.extractCountryCodeFromMessage(request.message);
    if (!countryCode) {
      missingParams.push('countryCode');
    }
  }
}
```

### 优点

✅ **提前识别**：在执行 plan 之前就识别出缺失参数，避免执行失败  
✅ **性能优化**：响应时间从 ~70 秒降低到 ~5 秒  
✅ **资源节省**：避免执行可能失败的 skills，节省计算资源  
✅ **用户体验**：快速返回澄清问题，无需等待超时  

### 潜在问题

⚠️ **验证规则维护**：需要为每个 skill 手动添加验证规则，可能遗漏  
⚠️ **参数依赖关系**：某些参数可能依赖前面步骤的结果，验证时可能无法准确判断  
⚠️ **动态参数**：某些参数可能通过 LLM 动态生成，验证时无法提前判断  

### 建议

1. **扩展验证规则**：
   - 考虑使用 skill 的 metadata 定义必需参数
   - 或者从 skill 的 TypeScript 接口自动提取必需参数

2. **处理参数依赖**：
   - 对于依赖前面步骤结果的参数，在验证时考虑前面步骤的输出
   - 或者标记为"运行时验证"，不在此阶段验证

3. **错误处理**：
   - 如果验证逻辑出错，应该降级到原来的执行后验证方式
   - 确保不会因为验证逻辑问题导致正常请求失败

## 🏗️ 架构师评审

### 当前架构分析

**设计模式**：
- **验证模式（Validation Pattern）**：在执行前验证输入，提前发现问题
- **快速失败（Fail Fast）**：尽早发现问题，避免浪费资源

**流程设计**：
```
优化前：
选择 Skills → 编排执行计划 → 执行 plan → Skill 执行失败 → 返回澄清问题

优化后：
选择 Skills → 编排执行计划 → ✅ 验证计划输入参数 → 如果缺少参数，立即返回澄清问题
                                                      → 如果参数完整，执行 plan
```

### 架构问题深度分析

#### 问题 1：硬编码验证规则 ⚠️ 严重

**问题**：
- 每个 skill 的验证逻辑都硬编码在 `validatePlanInputs` 中
- 新增 skill 需要手动添加验证规则
- 验证逻辑与 skill 内部验证可能重复
- 维护成本高，容易遗漏

**影响**：
- ❌ 可扩展性差（需要修改核心代码才能添加新 skill 的验证）
- ❌ 维护成本高（验证逻辑分散，难以统一管理）
- ❌ 容易出错（可能遗漏某些 skill 的验证规则）

#### 问题 2：验证时机过晚 ⚠️ 中等

**问题**：
- 验证在 plan 编排之后，已经消耗了 3-4 次 LLM 调用
- 如果验证失败，前面的 LLM 调用成本浪费

**影响**：
- ❌ 成本浪费（每次验证失败浪费 ~$0.01-0.02 的 LLM 成本）
- ❌ 响应时间仍然较长（~5-10 秒）

#### 问题 3：验证逻辑不完整 ⚠️ 中等

**问题**：
- 初始只验证了 3 个 skill（`decision.runThreeGuardians`、`world.buildContext`、`routeDirection.pickForIntent`）
- 其他 skill 的验证规则缺失
- 参数依赖关系无法处理（某些参数依赖前面步骤的结果）

**影响**：
- ❌ 验证覆盖不完整（初始只有 ~7% 的 skill 有验证规则）
- ✅ **已优化**：现在已覆盖 ~32% (14/44 skills)
- ❌ 某些 skill 仍然可能执行失败

#### 问题 4：参数提取逻辑复杂 ⚠️ 轻微

**问题**：
- `prepareSkillInput` 包含复杂的参数提取逻辑
- 验证时使用的输入可能与实际执行时的输入有差异
- 参数提取逻辑分散在多个地方

**影响**：
- ❌ 验证准确性可能不足
- ❌ 代码复杂度高

### 架构优化方案

**详细方案请参考**：`.claude/改动资料/架构师-架构优化方案-提前验证参数-2025-01-14.md`

#### 推荐方案：混合方案（分阶段实施）

**阶段 1：短期优化（立即实施）**
- 提取验证规则到配置对象
- 提前验证时机（在 Skills 选择之后，plan 编排之前）
- 添加更多 skill 的验证规则

**阶段 2：中期优化（1-2 个月）**
- 扩展 SkillMetadata 接口，添加 inputSchema
- 实现统一的验证服务
- 逐步迁移到声明式验证

**阶段 3：长期优化（3-6 个月）**
- 考虑基于 TypeScript 类型的自动提取
- 支持复杂的依赖关系处理

### 架构优点（优化后）

✅ **声明式验证**：验证规则定义在 skill metadata 中，清晰明确  
✅ **可扩展性强**：新增 skill 只需定义 metadata，无需修改验证逻辑  
✅ **统一接口**：所有 skill 使用统一的验证接口  
✅ **提前验证**：在 Skills 选择阶段就进行验证，节省 LLM 成本  
✅ **自动提取**：支持参数提取器，自动从 context/request 中提取参数  

### 建议

1. **立即实施**：
   - 提取验证规则到配置对象（减少硬编码）
   - 提前验证时机（在 Skills 选择之后，plan 编排之前）

2. **短期优化**：
   - 扩展 SkillMetadata 接口，添加 inputSchema
   - 实现统一的验证服务
   - 为核心 skill 添加 inputSchema

3. **长期优化**：
   - 全面迁移到声明式验证
   - 考虑基于类型的自动提取
