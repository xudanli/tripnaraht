# TripNARA 助手对话界面 - 场景与边界定义

**文档版本**：v1.0  
**创建时间**：2026-01-26  
**产品经理**：Danny  
**目标**：确保每个对话场景动作闭环，符合用户心智模型

---

## 一、核心原则

### 1.1 闭环原则
- **定义**：用户发起一个意图，系统必须完成该意图的完整执行，不能停留在中间状态
- **标准**：用户说"我要X"，系统应该直接给出X的结果，而不是问"你想要什么样的X？"
- **例外**：只有在信息确实不足且无法推断时，才允许询问澄清

### 1.2 用户心智模型
- **预期一致性**：系统提示的内容必须与实际数据一致
- **可执行性**：所有"接受建议"按钮必须真正执行操作
- **即时反馈**：操作后立即看到结果，不需要刷新或重新加载

### 1.3 场景边界
- **明确触发条件**：每个场景有明确的触发条件
- **明确结束状态**：每个场景有明确的成功/失败结束状态
- **明确异常处理**：每个场景有明确的异常和边界情况处理

## 二、核心对话场景

### 场景1：填充空闲时间（FILL_FREE_TIME）

#### 2.1.1 场景描述
用户希望系统帮助填充行程中的空闲时间段，添加合适的活动或餐厅。

#### 2.1.2 用户心智模型
- **用户说**："帮我填充空闲时间" / "添加餐厅和填充空闲时间"
- **用户期望**：系统直接推荐具体活动，而不是询问"你想添加什么？"
- **用户预期结果**：看到推荐列表，可以一键添加到行程

#### 2.1.3 触发条件
- 用户意图：`FILL_FREE_TIME` 或包含"填充"、"空闲"、"添加活动"等关键词
- 前置条件：行程中存在空闲时间段（> 30分钟）

#### 2.1.4 闭环流程

**步骤1：检测空闲时间**
```
输入：当前行程上下文
处理：分析所有天的行程，找出空闲时间段
输出：空闲时间段列表（day, start, end, duration）
```

**步骤2：主动推荐（必须）**
```
输入：空闲时间段 + 当天已有行程位置
处理：
  - 根据时间段类型判断推荐类型（早餐/午餐/晚餐/活动）
  - 根据当天行程位置推荐附近POI
  - 调用推荐引擎获取3-5个候选
输出：推荐活动列表（每个包含：名称、类型、位置、理由、一键添加按钮）
```

**步骤3：展示推荐结果**
```
响应格式：
{
  message: "我为您推荐以下活动来填充空闲时间：",
  recommendations: [
    {
      day: 1,
      timeSlot: { start: "12:00", end: "14:00" },
      suggestions: [
        {
          id: "rec_1",
          name: "当地特色餐厅",
          type: "RESTAURANT",
          location: "距离当前行程500米",
          reason: "午餐时间，体验地道美食",
          action: "ADD_TO_ITINERARY", // 一键添加
          placeId: "xxx"
        },
        // ... 更多推荐
      ]
    }
  ],
  quickActions: [
    { id: "refresh", label: "🔄 刷新推荐", action: "REFRESH_RECOMMENDATIONS" }
  ]
}
```

**步骤4：用户操作处理**
- **用户点击"一键添加"**：
  - 立即将活动添加到行程
  - 更新空闲时间计算
  - 返回确认消息："已添加「XXX」到第X天XX:XX"
  - 如果该时间段还有其他空闲，继续显示推荐

- **用户说"换一批"**：
  - 重新生成推荐（不同POI）
  - 保持相同时间段和类型

- **用户说"不需要"**：
  - 标记该时间段为"用户已拒绝推荐"
  - 不再主动推荐该时间段

#### 2.1.5 边界情况

| 情况 | 处理方式 |
|------|---------|
| 空闲时间 < 30分钟 | 提示："空闲时间较短，建议保持休息" |
| 找不到合适推荐 | 提示："该时间段暂无合适推荐，您可以手动添加" |
| 用户拒绝所有推荐 | 不再主动推荐，但保留手动添加入口 |
| 推荐引擎失败 | 降级为通用推荐（基于时间段类型） |

#### 2.1.6 验收标准
- ✅ 用户说"填充空闲时间"后，系统直接展示推荐列表（不询问）
- ✅ 推荐包含餐厅（如果空闲时段是餐点时间）
- ✅ 推荐位置与当天行程相关
- ✅ 用户可以直接点击"添加到行程"完成操作
- ✅ 添加后空闲时间自动更新

### 场景2：接受建议并执行（APPLY_SUGGESTION）

#### 2.2.1 场景描述
Abu（安全与边界守护者）或其他顾问给出建议，用户点击"接受建议"，系统必须执行该建议。

#### 2.2.2 用户心智模型
- **用户看到**：Abu提示"第1天01:00开始可能太早" + "接受建议"按钮
- **用户期望**：点击后，时间自动调整为合理时间（如08:00），提示消失
- **用户预期结果**：行程项时间已更新，警告消失，看到确认消息

#### 2.2.3 触发条件
- 用户点击"接受建议"按钮
- 建议类型包括：`timing`、`early_start`、`late_end`、`distance`、`overlap`等

#### 2.2.4 闭环流程

**步骤1：解析建议类型**
```
输入：suggestionId, suggestionType
处理：
  - 映射建议类型到操作类型
  - 加载建议详情（目标行程项、当前值、建议值）
输出：操作类型 + 操作参数
```

**步骤2：执行操作（必须实现）**

**2.2.4.1 时间调整（modify_time）**
```
处理逻辑：
1. 找到目标行程项（最早的那个，或指定的itemId）
2. 计算合理的新时间：
   - early_start: 调整为 08:00（或用户偏好时间）
   - late_end: 调整为 22:00（或用户偏好时间）
   - 如果用户提供了newStartTime，使用用户指定值
3. 计算时间差，调整后续行程项（避免冲突）
4. 更新数据库
5. 更新内存状态
6. 重新评估（Abu再次检查，确认问题已解决）

返回：
{
  message: "已将「XXX」的开始时间从 01:00 调整为 08:00",
  item: {
    id: "item_xxx",
    startTime: "08:00",
    endTime: "10:00"
  },
  tripUpdate: {
    totalChanges: 3, // 包括目标项和后续调整的项
    modifiedItems: 3,
    affectedDays: [1]
  },
  suggestionStatus: "RESOLVED" // 建议已解决
}
```

**2.2.4.2 距离调整（adjust_distance）**
```
处理逻辑：
1. 找到距离过大的两个行程项
2. 在中间插入交通项或调整顺序
3. 更新数据库和内存状态

返回：类似时间调整
```

**2.2.4.3 重叠调整（resolve_overlap）**
```
处理逻辑：
1. 找到重叠的行程项
2. 调整其中一个的时间或移除
3. 更新数据库和内存状态

返回：类似时间调整
```

**步骤3：更新UI状态**
```
- 前端立即更新行程项显示
- 移除或更新Abu的警告提示
- 显示成功消息："✓ 已应用建议"
```

#### 2.2.5 边界情况

| 情况 | 处理方式 |
|------|---------|
| 建议已过期（行程已修改） | 提示："行程已更新，该建议可能不再适用"，重新评估 |
| 调整后产生新冲突 | 自动检测并提示："调整后可能影响其他安排，是否继续？" |
| 数据库更新失败 | 至少更新内存状态，提示："已更新，但保存失败，请稍后重试" |
| 用户撤销操作 | 支持撤销，恢复到调整前状态 |

#### 2.2.6 验收标准
- ✅ 点击"接受建议"后，系统立即执行操作
- ✅ 操作后，Abu的警告消失或更新为"✓ 已解决"
- ✅ 行程项时间/内容立即更新（无需刷新）
- ✅ 如果影响其他项，自动调整并告知用户
- ✅ 数据库正确保存更改

### 场景3：时间数据一致性（TIME_CONSISTENCY）

#### 2.3.1 场景描述
确保Abu提示的时间与实际行程项显示的时间完全一致。

#### 2.3.2 用户心智模型
- **用户看到**：Abu提示"第1天01:00开始可能太早"
- **用户查看行程**：显示"09:00-11:00 斯卡夫塔山国家公园"
- **用户困惑**：为什么提示01:00，但显示09:00？系统不可信

#### 2.3.3 问题根源
- 时间数据源不一致（数据库原始值 vs 计算值 vs 显示值）
- 时区转换问题（UTC vs 本地时间）
- 时间格式解析错误（ISO格式 vs HH:mm格式）

#### 2.3.4 解决方案

**统一时间数据源**
```
所有时间操作必须：
1. 使用 normalizeTimeField() 标准化时间
2. 统一使用本地时间（用户时区）
3. 存储时转换为UTC，显示时转换回本地时间
4. 所有比较操作使用标准化后的时间
```

**时间解析逻辑**
```typescript
private normalizeTimeField(time: any): string | null {
  if (!time) return null;
  
  // 如果是Date对象
  if (time instanceof Date) {
    return this.formatTimeToHHmm(time);
  }
  
  // 如果是ISO字符串
  if (typeof time === 'string' && time.includes('T')) {
    const date = new Date(time);
    return this.formatTimeToHHmm(date);
  }
  
  // 如果已经是HH:mm格式
  if (typeof time === 'string' && /^\d{2}:\d{2}$/.test(time)) {
    return time;
  }
  
  return null;
}

private formatTimeToHHmm(date: Date): string {
  // 使用用户时区格式化
  const hours = date.getHours().toString().padStart(2, '0');
  const minutes = date.getMinutes().toString().padStart(2, '0');
  return `${hours}:${minutes}`;
}
```

**Abu评估时的时间检查**
```typescript
// 在 evaluateWithAbu 中
const normalizedTime = this.normalizeTimeField(earliestActivity.startTime);
if (normalizedTime) {
  const timeParts = normalizedTime.split(':');
  const startHour = parseInt(timeParts[0], 10);
  
  // 使用标准化后的时间进行比较
  if (startHour < 6) {
    // 提示时显示标准化后的时间
    return {
      type: 'timing',
      message: `第${day}天${normalizedTime}开始可能太早`,
      // ...
    };
  }
}
```

#### 2.3.5 验收标准
- ✅ Abu提示的时间必须与行程项显示的时间完全一致
- ✅ 如果行程项显示09:00，Abu不应该提示01:00
- ✅ 时区转换正确，不会出现时间偏移
- ✅ 时间解析能正确处理所有格式（ISO、HH:mm、Date对象）

### 场景4：添加活动（ADD_ACTIVITY）

#### 2.4.1 场景描述
用户希望添加特定活动到行程中。

#### 2.4.2 用户心智模型
- **用户说**："添加浅草寺" / "想去一个适合拍照的地方"
- **用户期望**：系统找到合适的地点，询问添加到哪一天，然后直接添加
- **用户预期结果**：活动已添加到行程，看到确认消息

#### 2.4.3 触发条件
- 用户意图：`ADD_ACTIVITY`
- 包含地点名称、活动类型、POI名称等

#### 2.4.4 闭环流程

**步骤1：理解用户意图**
```
输入：用户消息
处理：
  - 提取地点名称/类型
  - 如果明确指定地点，直接搜索
  - 如果是类型描述，调用推荐引擎
输出：目标POI列表（1个或多个候选）
```

**步骤2：确定添加位置**
```
如果用户未指定日期：
  - 分析空闲时间段
  - 推荐最合适的天和时间段
  - 询问："建议添加到第X天XX:XX，是否确认？"

如果用户指定了日期：
  - 直接使用指定日期
  - 分析该天的空闲时间，选择合适时间段
```

**步骤3：执行添加**
```
处理：
1. 创建行程项
2. 计算合理的时间（考虑前后行程）
3. 更新数据库
4. 更新内存状态
5. 重新计算空闲时间

返回：
{
  message: "已添加「浅草寺」到第1天 14:00-16:00",
  item: {
    id: "item_xxx",
    name: "浅草寺",
    day: 1,
    startTime: "14:00",
    endTime: "16:00"
  },
  tripUpdate: { ... }
}
```

#### 2.4.5 边界情况

| 情况 | 处理方式 |
|------|---------|
| 找不到指定地点 | 提供相似地点推荐："未找到'XXX'，是否指'YYY'？" |
| 所有天都排满 | 提示："行程已满，需要移除其他活动吗？" |
| 时间冲突 | 自动调整时间或询问："该时间段已有安排，是否调整？" |

#### 2.4.6 验收标准
- ✅ 用户说地点名称后，系统找到并添加（不需要再次确认地点）
- ✅ 如果未指定日期，系统推荐最合适的天
- ✅ 添加后立即在行程中显示
- ✅ 时间自动计算，考虑前后行程

### 场景5：优化行程（OPTIMIZE_ROUTE）

#### 2.5.1 场景描述
用户希望优化行程路线，调整顺序，减少交通时间。

#### 2.5.2 用户心智模型
- **用户说**："优化今天的行程" / "调整路线顺序"
- **用户期望**：系统分析当前路线，给出优化方案，用户确认后应用
- **用户预期结果**：行程顺序已优化，交通时间减少

#### 2.5.3 触发条件
- 用户意图：`OPTIMIZE_ROUTE`
- 包含"优化"、"调整顺序"、"路线"等关键词

#### 2.5.4 闭环流程

**步骤1：分析当前路线**
```
处理：
1. 获取指定天（或所有天）的行程项
2. 计算当前总交通时间
3. 分析地理位置关系
4. 识别可优化的点

输出：当前路线分析报告
```

**步骤2：生成优化方案**
```
处理：
1. 调用路线优化算法
2. 生成新的顺序
3. 计算优化后的交通时间
4. 评估优化收益

输出：
{
  message: "优化方案：调整3个行程项顺序，预计节省45分钟交通时间",
  currentRoute: [...],
  optimizedRoute: [...],
  benefits: {
    savedTime: 45, // 分钟
    reducedDistance: 12.5 // 公里
  },
  action: "APPLY_OPTIMIZATION" // 一键应用
}
```

**步骤3：应用优化**
```
用户点击"应用优化"后：
1. 更新行程项顺序
2. 重新计算时间
3. 更新数据库
4. 更新内存状态

返回：
{
  message: "✓ 已优化行程，节省45分钟交通时间",
  tripUpdate: { ... }
}
```

#### 2.5.5 边界情况

| 情况 | 处理方式 |
|------|---------|
| 无法优化（已最优） | 提示："当前路线已是最优，无需调整" |
| 优化收益很小 | 提示："优化后仅节省X分钟，是否仍要应用？" |
| 优化后时间冲突 | 自动调整时间，或提示："优化后需要调整时间，是否继续？" |

#### 2.5.6 验收标准
- ✅ 用户说"优化行程"后，系统直接给出优化方案（不询问）
- ✅ 显示优化前后的对比
- ✅ 用户可以直接点击"应用优化"完成操作
- ✅ 应用后行程立即更新

### 场景6：回答问题（ASK_QUESTION）

#### 2.6.1 场景描述
用户询问关于行程、目的地、天气、签证等问题。

#### 2.6.2 用户心智模型
- **用户说**："今天会下雨吗？" / "这个景点需要预约吗？"
- **用户期望**：系统直接回答，提供准确信息
- **用户预期结果**：得到答案，可能包含相关建议

#### 2.6.3 触发条件
- 用户意图：`ASK_QUESTION`
- 包含疑问词或问号

#### 2.6.4 闭环流程

**步骤1：理解问题**
```
处理：
1. 分析问题类型（天气/签证/费用/预约/交通等）
2. 提取关键信息（日期、地点等）
3. 确定需要调用的技能/API

输出：问题类型 + 查询参数
```

**步骤2：获取答案**
```
根据问题类型：
- 天气：调用天气查询技能
- 签证：调用知识库或RAG
- 费用：分析行程预算
- 预约：查询POI信息
- 交通：分析行程中的交通安排

输出：答案 + 数据来源
```

**步骤3：格式化回答**
```
返回：
{
  message: "根据天气预报，第1天（1月26日）冰岛雷克雅未克地区：\n- 温度：2°C / -1°C\n- 天气：多云，有小雪\n- 建议：携带保暖衣物，注意防滑",
  data: {
    source: "weather_api",
    date: "2026-01-26",
    location: "Reykjavik"
  },
  suggestions: [
    { label: "查看7天天气预报", action: "SHOW_WEATHER_FORECAST" }
  ]
}
```

#### 2.6.5 边界情况

| 情况 | 处理方式 |
|------|---------|
| 无法获取数据 | 提示："暂时无法获取该信息，请稍后重试" |
| 信息不完整 | 提供部分信息，说明："部分信息可能不准确" |
| 问题超出范围 | 礼貌说明："我主要帮助规划行程，这个问题建议咨询..." |

#### 2.6.6 验收标准
- ✅ 用户提问后，系统直接回答（不询问澄清，除非确实无法理解）
- ✅ 答案准确，有数据来源
- ✅ 如果涉及行程，提供相关建议

### 场景7：显示概览（SHOW_OVERVIEW）

#### 2.7.1 场景描述
用户希望查看行程的整体概览，了解安排情况。

#### 2.7.2 用户心智模型
- **用户说**："显示行程概览" / "看看整体安排"
- **用户期望**：看到结构化的行程总结，包括天数、主要活动、空闲时间等
- **用户预期结果**：清晰的概览信息，可以快速了解行程

#### 2.7.3 触发条件
- 用户意图：`SHOW_OVERVIEW`
- 包含"概览"、"总结"、"整体"等关键词

#### 2.7.4 闭环流程

**步骤1：分析行程**

## 三、通用交互模式

### 3.1 快速操作按钮
所有场景都应提供快速操作按钮，但按钮必须：
- **有明确动作**：点击后立即执行，不再次询问
- **有即时反馈**：执行后立即显示结果
- **可撤销**：重要操作支持撤销

### 3.2 多轮对话处理
- **上下文记忆**：记住用户之前的操作和偏好
- **渐进式细化**：如果信息不足，逐步询问，但每次询问后必须推进
- **避免循环**：同一问题最多问2次，第3次使用默认值或跳过

### 3.3 错误处理
- **明确错误信息**：告诉用户具体出了什么问题
- **提供解决方案**：不仅说"失败"，还要说"可以尝试..."
- **降级处理**：主要功能失败时，提供降级方案

## 四、数据一致性要求

### 4.1 时间一致性
- ✅ 所有时间显示使用同一数据源
- ✅ 时区转换统一处理
- ✅ 时间格式统一（HH:mm）

### 4.2 状态一致性
- ✅ 内存状态与数据库状态同步
- ✅ 前端显示与后端数据一致
- ✅ 操作后立即更新所有相关状态

### 4.3 建议一致性
- ✅ Abu的建议基于最新行程数据
- ✅ 建议应用后，重新评估确保问题解决
- ✅ 如果建议已不适用，自动清除或更新
