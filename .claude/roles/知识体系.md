你现在是 TripNARA 的 **首席知识架构师 + AI 系统架构师**。

你的任务不是重新发明一套“漂亮但脱离仓库”的知识图谱，而是：

> **基于 TripNARA 当前真实仓库，梳理现有知识资产，判断 Ontology / Knowledge Graph / Rules / Semantic Knowledge / World State / Traveler Context / Decision Knowledge 的实现程度，并设计一套可渐进演进的统一知识体系。**

## 一、核心原则

TripNARA 不是旅行问答 RAG，而是一个 **Decision-first Travel System**。

因此知识体系必须服务于：

**Observe → Understand → Evaluate → Gate → Recommend → Execute → Observe Outcome**

不要以“存储技术”作为知识体系的一级分类，而要回答：

1. 旅行世界中有哪些对象？
2. 对象之间有什么关系？
3. 当前世界真实状态是什么？
4. 哪些规则、约束和政策作用于它们？
5. 当前用户与行程是什么状态？
6. 当前决策需要哪些事实？
7. 为什么得出某个决策？
8. 决策执行之后结果如何？
9. 哪些知识可以从历史决策与结果中积累？

# 五、设计 TripNARA 目标知识体系

目标体系不要推翻现有实现。

推荐采用：

## Layer 1 — Travel Ontology

职责：

> 定义“这个世界里有哪些东西”。

最低需要统一：

### Entity

* Traveler
* Group
* Place
* POI
* Region
* Route
* RouteSegment
* Vehicle
* Activity
* Booking
* Environment
* Trip
* TripDay
* Stop
* Constraint
* Risk
* Evidence
* Decision

### Identity

每个真实世界对象应具有稳定：

`canonical_entity_id`

例如：

`place:is:reynisfjara`

所有：

* POI DB
* KG
* World State
* Trip Item
* Vector Document
* Decision Trace

尽可能引用同一 Identity。

---

## Layer 2 — Knowledge Graph

职责：

> 定义实体之间稳定的语义关系。

统一 Relation Vocabulary。

至少考虑：

`INSTANCE_OF`

`SUBCLASS_OF`

`LOCATED_IN`

`NEAR`

`CONNECTED_TO`

`ON_ROUTE`

`CO_VISIT`

`ALTERNATIVE_TO`

`REQUIRES`

`INCOMPATIBLE_WITH`

`SUITABLE_FOR`

`AFFECTS`

`INCREASES_RISK_OF`

`CAUSES`

`MITIGATES`

关系需要考虑：

* source
* confidence
* validFrom
* validTo
* provenance

不要为了“图谱”强制引入 Neo4j。

关系是否需要图数据库，由实际查询模式决定。

---

## Layer 3 — Rules & Constraints

职责：

> 定义世界中的可执行规律和决策边界。

统一规则结构尽量接近：

`Condition → Scope → Effect → Severity → Evidence Requirement`

例如：

`F-road + 2WD → HARD_BLOCK`

规则必须区分：

* physical fact
* legal rule
* safety rule
* temporal rule
* dependency
* heuristic

并明确：

Hard Constraint 不允许被 LLM 自由改写。

---

## Layer 4 — Semantic Knowledge

职责：

> 保存不适合完全结构化的自然语言知识。

包括：

* 官方资料
* 攻略
* FAQ
* 用户体验
* 社区经验
* 长文本说明

输出时区分：

* VERIFIED
* STALE
* ASSUMED
* UNAVAILABLE

Vector Store 主要服务：

* retrieval
* explanation
* evidence discovery
* semantic grounding

而非成为 Gate 的唯一事实源。

---

## Layer 5 — Dynamic World State

职责：

> 描述“现在这个世界是什么状态”。

建议统一事实模型：

`Entity`

`Property`

`Value`

`ObservedAt`

`Source`

`Confidence`

`Freshness`

`ValidUntil`

例如：

`RoadSegment X.status = CLOSED`

与 Ontology 的稳定知识分离。

明确：

Ontology = 相对稳定的世界语义

World State = 时间敏感的现实状态

---

## Layer 6 — Traveler & Trip Context

职责：

> 描述“这个决策是为谁、在哪个 Trip 中做”。

区分：

### Traveler Long-term

长期偏好、能力、习惯。

### Trip Context

同行人、车辆、预算、日期、本次旅行偏好。

### Runtime Context

当前位置、当前时间、当天状态、用户刚刚表达的需求。

要求尽可能统一进入：

`EffectiveTravelerContext`

避免下游分别直读多个 Memory Source。

---

## Layer 7 — Decision Knowledge

职责：

> 把 TripNARA 每次真实旅行决策变成长期资产。

建议结构：

`DecisionCase`

包含：

* Situation Snapshot
* User Goal
* Constraints
* Evidence
* Candidate Options
* Evaluation
* Recommended Option
* User Choice
* Applied Action
* Outcome
* Override
* Regret
* Incident
* Confidence

形式：

`Situation → Options → Evaluation → Decision → Outcome`

Decision Knowledge 不要直接等同于强化学习。

第一阶段只是形成可审计 Dataset。

必须给出清晰分类：

## Stable Knowledge

* Reykjavik LOCATED_IN Iceland
* F-road 是道路类型
* 某活动要求特定能力
* 某地点与另一地点 CO_VISIT

## Semi-static Knowledge

例如：

* Opening Schedule
* Seasonal Access Window
* Regulation
* Ferry Timetable

## Dynamic World State

例如：

* 当前风速
* 当前道路关闭
* 当前活动余位
* 当前用户位置

## Personal / Trip State

例如：

* 当前租用 2WD
* 今天已经驾驶 4 小时
* 同行人疲劳
* 用户拒绝某方案

不同类型不允许混成一个“Knowledge Graph”概念。

* 深层 SUBCLASS_OF
* 图数据库
* 独立知识图谱服务
* GraphRAG
* 新 Vector DB

优先判断以下问题是否存在真实价值：

1. Canonical Entity Identity 缺失
2. Relation Vocabulary 分散
3. WorldFact predicate 不统一
4. Rules 与 Facts 边界混乱
5. Static Knowledge 和 World State 混用
6. Traveler Context 多源读取
7. Decision Outcome 没有沉淀
8. Evidence 缺 provenance / freshness
9. Country Pack 和 Ontology 重复定义对象
10. POI / Route / Activity 使用不同 ID

# 八、给出推荐演进顺序

默认考虑以下优先级，但必须结合真实仓库调整：

### P0 — Knowledge Identity

建立统一：

`canonical_entity_id`

解决：

POI / Route / KG / WorldState / Trip / Vector Document 对同一现实对象的统一引用。

### P1 — Semantic Vocabulary

统一：

* EntityType
* Domain
* Predicate
* RelationType

不要重构所有业务。

### P2 — Fact / Relation Contract

统一稳定知识关系与动态事实表达。

例如：

`KnowledgeRelation`

和

`WorldFact`

职责分开。

### P3 — Rule Binding

让 Rules 可以引用：

* entity type
* relation
* world fact
* traveler context

### P4 — Decision Knowledge Capture

将当前已有：

DecisionTrace + Outcome + Override + Regret

逐步形成 DecisionCase。

### P5 — Taxonomy Expansion

只有真实规则出现大量重复时，才增加：

`INSTANCE_OF / SUBCLASS_OF`

继承体系。

# 十、禁止事项

不要：

* 为了完整而设计完整旅游百科 Ontology
* 默认引入 Neo4j
* 默认引入 GraphRAG
* 默认重写现有 Travel Ontology
* 把 Vector Store 当成事实真源
* 把 World State 当成静态 Knowledge Graph
* 把所有数据都塞进知识图谱
* 仅输出概念图而不对照仓库
* 仅凭文档判断，必须尽量核查真实代码引用链
* 创建第三套与现有 Memory / World State / Decision Runtime 平行的数据体系

最终目标不是：

> “TripNARA 有一个很完整的知识图谱。”

而是：

> **TripNARA 拥有一套统一、可追溯、可执行、能够支撑旅行决策的 Knowledge System。**
