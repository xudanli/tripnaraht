# 多角色 Agent 协作机制

## 概述

本文档描述 TripNARA 项目中各个**辅助角色**（产品经理、智能体工程师、LangGraph 工程师、全局工程系统、路线与优化算法工程师等）的协作机制。

**注意**：本文档描述的是**辅助角色**（帮助用户写代码的角色），不是系统运行时使用的 Agent。系统 Agent 文档请参考 `prompts/agents/README.md`。

## 详细协作场景

### 场景 1: 新功能开发（端到端）

#### 阶段 1: 需求定义（产品经理主导）

**产品经理**：
- 收集用户需求
- 撰写 PRD 文档（参考 `product-manager.md`）
- 明确功能边界、验收标准

**输出**：
- PRD 文档（包含 0.1-0.21 章节）
- 需求清单
- 验收标准

**协作点**：
- 与架构师确认技术可行性
- 与路线优化算法工程师确认算法约束

#### 阶段 2: 架构设计（架构师主导）

**架构师**：
- 设计总体架构（数据层、模型层、服务层、API 层、前端层、观测层）
- 定义关键模块边界与职责
- 设计数据流与控制流
- 定义降级与容灾策略
- 定义成本控制策略
- 定义版本与灰度策略
- 识别风险清单与缓解措施

**输出**：
- 总体架构图
- 模块边界定义
- 数据流与控制流设计
- 降级策略文档
- 成本控制策略
- 版本策略
- 风险清单

**协作点**：
- 与产品经理确认业务需求理解
- 与智能体工程师确认 Agent 设计
- 与路线优化算法工程师确认算法接口
- 与 LangGraph 工程师确认编排方式（如果需要）

#### 阶段 3: 详细设计（智能体工程师主导）

**智能体工程师**：
- 基于架构师的总体架构，设计 Agent 层
- 确定编排模式（LEGACY / CLAUDE_DYNAMIC / CLAUDE_SM）
- 设计 Skills 和 Sub-Agents 接口
- 设计状态机流程

**输出**：
- Agent 设计文档
- Skills 清单和接口定义
- Sub-Agents 协作流程
- 状态机流程定义

**协作点**：
- 与架构师确认符合总体架构
- 与路线优化算法工程师确认算法接口
- 与 LangGraph 工程师确认编排方式（如果需要）

#### 阶段 4: 算法设计（路线优化算法工程师主导）

**路线优化算法工程师**：
- 设计路线生成算法
- 定义约束规则（硬门控 + 软评分）
- 设计评估指标

**输出**：
- 算法设计文档
- 约束规则定义
- 评估指标定义
- 回归测试集

**协作点**：
- 与智能体工程师确认接口定义
- 与产品经理确认业务规则

#### 阶段 5: 代码实现（全局工程系统主导）

**全局工程系统**：
- 实现 Skills（如果涉及）
- 实现 Sub-Agents（如果涉及）
- 实现算法逻辑（如果涉及）
- 编写测试用例

**输出**：
- 代码实现
- 单元测试
- 集成测试

**协作点**：
- 参考智能体工程师的架构设计
- 参考路线优化算法工程师的算法设计
- 确保符合产品经理的验收标准

#### 阶段 6: 编排集成（LangGraph 工程师，如需要）

**LangGraph 工程师**（如果需要新的编排方式）：
- 设计 LangGraph 图结构
- 实现节点逻辑
- 实现 Merge & Decide 逻辑
- 实现 Approval Gate

**输出**：
- LangGraph 图定义
- 节点实现
- 测试用例

**协作点**：
- 与智能体工程师确认是否需要 LangGraph
- 与全局工程系统确认集成方式

#### 阶段 7: 集成测试（架构师主导，全局工程系统执行）

**全局工程系统**：
- 端到端测试
- 性能测试
- 回归测试

**架构师**：
- 验收架构实现
- 验收可观测性指标
- 验收降级策略

**协作点**：
- 所有角色参与验收
- 产品经理确认符合 PRD
- 架构师确认符合架构设计
- 智能体工程师确认 Agent 设计符合要求

### 场景 2: Skills 开发

#### 触发：需要新的能力

**架构师**（如涉及系统级变更）：
1. 评估新 Skill 对系统架构的影响
2. 确认是否符合架构原则

**智能体工程师**：
1. 分析需求，确定是否需要新 Skill
2. 设计 Skill 接口（输入/输出 schema）
3. 定义 Skill 的职责和边界

**路线优化算法工程师**（如果涉及路线优化）：
1. 如果 Skill 涉及路线优化，提供算法逻辑
2. 定义约束规则和评估指标

**全局工程系统**：
1. 实现 Skill（`src/skills/**/*.skill.ts`）
2. 在 SkillsModule 中注册
3. 编写测试用例

**协作流程**：
```
架构师（架构评估，如需要）
    ↓
智能体工程师（接口设计）
    ↓
路线优化算法工程师（算法逻辑，如适用）
    ↓
全局工程系统（代码实现）
    ↓
智能体工程师（验收）
```

### 场景 3: Sub-Agent 开发

#### 触发：需要新的 Sub-Agent

**产品经理**：
1. 定义 Sub-Agent 的职责（是否暴露给用户？）
2. 确定三人格映射（Abu/Dr.Dre/Neptune）

**架构师**：
1. 评估新 Sub-Agent 对系统架构的影响
2. 确认是否符合架构原则（决策优先、可观测、可降级）

**智能体工程师**：
1. 设计 Sub-Agent 接口（`src/agent/interfaces/sub-agent.interface.ts`）
2. 确定在状态机中的位置（哪个步骤调用？）
3. 设计与其他 Sub-Agents 的协作方式

**全局工程系统**：
1. 实现 Sub-Agent（`src/agent/services/sub-agents/*.service.ts`）
2. 在 AgentModule 中注册
3. 编写测试用例

**协作流程**：
```
产品经理（职责定义）
    ↓
架构师（架构评估）
    ↓
智能体工程师（接口设计 + 状态机集成）
    ↓
全局工程系统（代码实现）
    ↓
产品经理 + 架构师 + 智能体工程师（验收）
```

### 场景 4: 路线优化算法改进

#### 触发：优化指标不达标或需要新功能

**路线优化算法工程师**：
1. 分析现有算法问题
2. 设计改进方案
3. 定义新的评估指标
4. 设计回归测试用例

**智能体工程师**：
1. 确认算法改进是否需要修改接口
2. 确认是否需要新的 Skills 支持

**全局工程系统**：
1. 实现算法改进
2. 更新相关 Skills（如 `itinerary.generate`）
3. 更新测试用例

**协作流程**：
```
路线优化算法工程师（算法设计）
    ↓
智能体工程师（接口确认）
    ↓
全局工程系统（代码实现）
    ↓
路线优化算法工程师（算法验收）
```

### 场景 5: LangGraph 编排引入

#### 触发：需要新的编排方式或增强现有编排

**产品经理**：
1. 定义新编排方式的业务需求
2. 确定与现有 CLAUDE_SM 状态机的关系

**架构师**：
1. 评估 LangGraph 对系统架构的影响
2. 设计集成架构
3. 定义数据流和控制流

**智能体工程师**：
1. 评估是否需要 LangGraph
2. 设计 LangGraph 与现有系统的集成方式

**LangGraph 工程师**：
1. 设计 LangGraph 图结构
2. 设计节点和边
3. 设计 Merge & Decide 逻辑
4. 设计 Approval Gate

**全局工程系统**：
1. 实现 LangGraph 图
2. 实现节点逻辑
3. 集成到现有系统

**协作流程**：
```
产品经理（需求定义）
    ↓
架构师（架构设计）
    ↓
智能体工程师（Agent 层设计）
    ↓
LangGraph 工程师（图设计）
    ↓
全局工程系统（代码实现）
    ↓
所有角色（集成验收）
```

## 协作原则

### 1. 职责边界

**产品经理**：
- 负责业务需求和验收标准
- 不涉及具体技术实现
- 但需要理解技术约束

**架构师**：
- 负责总体系统架构设计
- 负责模块边界和职责定义
- 负责降级、容灾、成本控制策略
- 负责可观测性设计
- 不涉及具体代码实现

**智能体工程师**：
- 负责 Agent 层设计（基于架构师的总体架构）
- 负责 Skills 和 Sub-Agents 的接口定义
- 负责状态机流程设计
- 不涉及具体算法实现（除非是 Agent 编排算法）

**路线优化算法工程师**：
- 负责路线优化算法设计
- 负责约束规则定义
- 不涉及系统架构设计

**LangGraph 工程师**：
- 负责 LangGraph 编排设计
- 负责图结构和节点设计
- 不涉及具体业务逻辑实现

**全局工程系统**：
- 负责代码实现
- 负责测试编写
- 不涉及业务需求定义和架构设计

### 2. 接口协议

**统一的数据合同**：
- 所有角色必须遵循 `src/agent/interfaces/trip-plan.interface.ts` 定义的数据合同
- `TripPlanRequest`、`GateResult`、`Itinerary`、`DecisionLogEntry` 等

**Skills 接口**：
- 所有 Skills 必须实现 `Skill<TInput, TOutput>` 接口
- 参考：`src/skills/interfaces/skill.interface.ts`

**Sub-Agent 接口**：
- 所有 Sub-Agents 必须实现对应的接口
- 参考：`src/agent/interfaces/sub-agent.interface.ts`

### 3. 协作时序

**设计阶段**：
1. 产品经理 → 架构师（需求澄清）
2. 架构师 → 智能体工程师（架构设计）
3. 智能体工程师 → 路线优化算法工程师（算法需求）
4. 智能体工程师 → LangGraph 工程师（编排需求，如需要）

**实现阶段**：
1. 全局工程系统实现代码
2. 各专业工程师提供技术指导

**验收阶段**：
1. 所有角色参与验收
2. 产品经理确认业务需求
3. 专业工程师确认技术实现

### 4. 文档要求

**每个角色必须输出**：
- **产品经理**：PRD 文档（0.1-0.21 章节）
- **架构师**：总体架构图、模块边界、数据流、降级策略、成本控制、版本策略、风险清单
- **智能体工程师**：Agent 设计文档、接口定义、状态机流程
- **路线优化算法工程师**：算法设计文档、约束规则、评估指标
- **LangGraph 工程师**：图设计文档、节点定义
- **全局工程系统**：代码实现、测试用例

## 常见协作问题

### Q1: 产品经理和架构师意见不一致怎么办？

**解决方案**：
- 优先遵循产品经理的业务需求
- 架构师可以提出技术约束和建议
- 如果技术约束不可行，架构师需提出替代方案
- 最终由产品经理决策，但需记录技术风险和缓解措施

### Q2: 算法工程师和智能体工程师接口定义不一致？

**解决方案**：
- 以智能体工程师的接口设计为准（保证系统一致性）
- 算法工程师可以在接口内实现算法逻辑
- 如需扩展接口，需与智能体工程师协商

### Q3: LangGraph 与现有 CLAUDE_SM 状态机冲突？

**解决方案**：
- LangGraph 作为补充编排方式，不替代 CLAUDE_SM
- 两者使用统一的数据合同和接口
- 通过路由策略选择使用哪种编排方式

### Q4: 全局工程系统实现与设计不一致？

**解决方案**：
- 全局工程系统应先与设计者确认差异原因
- 如果是实现困难，应记录并讨论替代方案
- 如果是设计问题，应反馈给设计者修改设计
